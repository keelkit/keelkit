# upgrade-site — обновление сайта Keelkit

Сайт Keelkit — самостоятельное Go-приложение: общий код приходит модулями Keelkit (зависимости `go.mod`), всё
остальное — код сайта, когда-то скопированный с эталона `reference/` монорепо `github.com/keelkit/keelkit`.
Обновление — это три вещи, в таком порядке:
1. **модули** — новая версия в `go.mod` и шаги из `UPGRADE.md` модуля для каждой пройденной версии;
2. **валидатор спецификации** — `SPEC_VERSION` в `Makefile` и шаги из `UPGRADE.md` модуля `spec`;
3. **эталон** — исправления и новые конвенции, появившиеся в `reference/` с тех пор, как сайт создан.

**Результат для человека — ветка с обновлением, где всё проверено, и понятный список того, что сделать на сервере.**
Живые данные не трогаем: миграции и повторная обработка изображений проверяются на копии, в прод их применяет
человек (или агент по его отдельной просьбе) по инструкции из итога.

Правила, которые здесь важнее скорости:
- Шаги `UPGRADE.md` — инструкция автора модуля: выполняй их буквально, по порядку версий, от старых к новым. Шаг не
  подходит сайту (сайт сделан иначе, чем эталон) — сделай то, чего шаг добивается, и скажи об этом в итоге.
- Новая **мажорная** версия модуля (путь `/v2` и дальше) — ломающие изменения: без согласия человека не переходить,
  только сообщить. Внутри `v0.x` ломающие изменения тоже бывают — их описывает `UPGRADE.md`.
- Тест падает — исправляй причину, а не тест. Ожидание теста меняется, только если `UPGRADE.md` или изменение
  эталона так и говорят (например, новая разметка), — и тогда это видно в итоге.

Аргументы: `$ARGUMENTS` — каталог сайта (по умолчанию текущий) и, если человек назвал, что обновить
(`images@v0.3.0`, `images`, «только spec»): тогда только это, без остального.

## 0. Проверить сайт и окружение

Остановись и скажи человеку, если:
- в каталоге нет `site.yaml` и `go.mod` с модулями `github.com/keelkit/keelkit/modules/*` — это не сайт Keelkit;
- каталог внутри монорепо Keelkit (выше есть `go.work` монорепо): обновление проверялось бы на неопубликованном коде;
- `git status` не чистый — незакоммиченные правки человека смешаются с обновлением (предложи закоммитить их сначала);
- в `go.mod` есть `replace` для модулей Keelkit — обновление версии ничего не даст.

Базовая линия — до любых правок: `make test`. Красная — не обновляй: сломанное до обновления нельзя отличить от
сломанного обновлением. Скажи человеку, что падает, и предложи сначала починить это (отдельной задачей).

## 1. Что обновлять

```sh
"${CLAUDE_SKILL_DIR}/scripts/upgrade-plan.sh" .
```

Скрипт печатает по каждому модулю Keelkit и по `spec` текущую и последнюю версию, путь к `UPGRADE.md` и
`CHANGELOG.md` последней версии (опубликованные файлы из кэша модулей Go) и разделы `UPGRADE.md`, которые нужно
выполнить; новую мажорную версию — отдельной строкой; строку об эталоне из `AGENTS.md` сайта. Ничего не меняет.

Прочитай `CHANGELOG.md` (что нового) и нужные разделы `UPGRADE.md` (что делать) каждого модуля к обновлению.

Эталон: из строки `AGENTS.md` сайта «создан `create-site` из эталона `<тег>` `<коммит>`» (или «обновлён
`upgrade-site` до эталона …» — бери последнюю) возьми коммит и посмотри, что изменилось:

```sh
"${CLAUDE_SKILL_DIR}/scripts/reference-diff.sh" <коммит> "$TMPDIR/reference.diff"
```

Печатает новую сторону (`reference: <тег> <коммит>`), коммиты и файлы; полный diff — в файл. `KEELKIT_REPO=<клон
монорепо>` — эталон из локального клона (разработка скиллов, эвалы). Строки об эталоне в `AGENTS.md` нет (сайт
старше плагина) — шаг эталона пропусти и скажи об этом в итоге.

Всё последнее и эталон не изменился — скажи человеку, что сайт актуален, и закончи.

**План — одно сообщение человеку**, без вопроса в конце: что поднимается (модуль: с какой версии на какую, одной
строкой — что нового), какие шаги потребуются (код, миграции модулей, повторная обработка изображений, изменения
`site.yaml`), что из эталона будет перенесено, что потребует действий на сервере. Вопрос — только если есть новая
мажорная версия или `UPGRADE.md` требует решения человека; иначе работай дальше.

## 2. Ветка

```sh
git rev-parse HEAD         # BASE — коммит до обновления, нужен на шаге 6
git switch -c keelkit-upgrade-<ГГГГ-ММ-ДД>
```

Каждый шаг ниже — отдельный коммит: его легко просмотреть и, если надо, откатить.

## 3. Модули

По одному модулю, в порядке `modules` из `site.yaml` (это порядок миграций). Для каждого:

1. Поднять версию сразу до последней (промежуточные ставить не нужно):
   `GOWORK=off GOFLAGS=-tags=nodynamic go get github.com/keelkit/keelkit/modules/<имя>@<версия>`, затем то же
   `go mod tidy`. Исключение — раздел `UPGRADE.md` требует развернуть промежуточную версию на сервере (например,
   двухэтапная миграция данных): остановись на ней, доведи до конца шаги 3–7 и скажи человеку, что следующая
   версия — после развёртывания этой.
2. Выполнить разделы `UPGRADE.md` от старой версии к новой. Образец того, как это сделано, — эталон: diff
   `reference/` из шага 1 обычно содержит те же правки (у эталона другой путь модуля и другие типы контента).
3. Новые миграции модуля меняют итоговую схему: `make schema` (снимок `db/schema.sql`).
4. `make generate`, `make test` — зелёные, затем коммит `<имя> v<старая> → v<новая>`.

Затем `spec`: `SPEC_VERSION ?= <версия>` в `Makefile` сайта, разделы `UPGRADE.md` модуля `spec` (правки `site.yaml`),
`make spec-validate`, коммит `spec v<старая> → v<новая>`. Мажорная версия модуля в `site.yaml` (`modules: { images: v0 }`)
меняется только вместе с путём `/vN`.

## 4. Эталон

Код сайта — копия эталона, приведённая к `site.yaml`. Изменение эталона переносится, если такой же код есть на
сайте; правь сайт так, чтобы получилось то же поведение, с учётом его отличий (свои типы, поля, тексты).
Прочитай diff по файлам и раздели изменения:

| Что изменилось в эталоне | Что делать |
|---|---|
| Общий код: `internal/admin`, `database`, `web`, `blocks`, `listfield`, `seofields`, `menu`, `settings`, `slug`, `media`, `filelib`, `cmd/site/main.go`, `backup.go`, `user.go`, `static/*.js`, `static/admin.css`, `Makefile`, `deploy/`, `Dockerfile`, `.golangci.yml`, версии Go и инструментов | перенести (исправления, безопасность, версии) |
| Типы контента эталона (`internal/content/<тип>`), `server.go`, общие стили `static/style.css` | перенести в типы сайта, сделанные по этому образцу, если это исправление или конвенция; вёрстку и тексты сайта не менять |
| Новая возможность (новый блок, тип поля, раздел админки) | не переносить; перечислить в итоге как «можно добавить» |
| Правки, которые сделали шаги 3 (новая версия модуля в `go.mod`, вызовы нового API) | уже сделаны — пропустить |
| Seed, тексты, тесты эталона о его контенте, история (`pages_legacy`, номера его миграций) | не переносить |
| `AGENTS.md` эталона: новые или изменённые конвенции | перенести в `AGENTS.md` сайта своими словами о сайте |
| Новая миграция эталона | только если она исправляет общее (например, индекс таблицы `menu_items`): новой миграцией сайта со следующим номером; меняет данные — сначала согласовать с человеком |

У переноса — тесты: если эталон добавил тест к перенесённому поведению, добавь такой же. Конфликт с правкой,
которую человек сделал на сайте нарочно (видно в `git log`), — оставь сайт как есть и скажи об этом в итоге.

В `AGENTS.md` сайта, раздел «Версии»: версии модулей и `spec`; строка Keelkit — «плагин `keelkit` ≥ <версия из
`plugin.json`>; создан `create-site` из эталона `<тег> <коммит>`, обновлён `upgrade-site` до эталона `<тег> <коммит>`»
(новая сторона — строка `reference:` из `reference-diff.sh`). Коммит «Эталон <старый коммит> → <тег>».

## 5. Проверка

Всё через `make`, в каталоге сайта; ошибка — исправить и повторить, а не обойти:

```sh
make generate && make schema
make lint
make test            # unit, e2e, контрактные тесты модулей (testkit) — первыми покажут сломанную интеграцию
make test-isolated   # только опубликованные версии модулей
make e2e-browser     # если есть Chrome
make spec-validate
"${CLAUDE_SKILL_DIR}/../create-site/scripts/check-site.sh" .
git add -A && git commit -m "…" && make generate-check   # если что-то осталось незакоммиченным
```

## 6. Миграции на копии данных

Новый код должен поднять базу, какой она была до обновления, — это то, что произойдёт на сервере.

```sh
"${CLAUDE_SKILL_DIR}/scripts/migrate-check.sh" <BASE>                 # база из миграций и seed кода до обновления
"${CLAUDE_SKILL_DIR}/scripts/migrate-check.sh" <BASE> data            # ещё и копия локальных данных человека, если есть data/site.db
REPROCESS_BELOW=<N> "${CLAUDE_SKILL_DIR}/scripts/migrate-check.sh" <BASE>   # UPGRADE.md images требует повторной обработки
```

Скрипт работает на копии во временном каталоге (переданный `DATA_DIR` только копируется): `make migrate` нового кода
(со снимком БД), повторная обработка (и её повторный запуск — он ничего не должен делать), `make run`, `/healthz` —
`pending: 0` у всех схем, главная — 200. Человек дал копию живой базы (`make backup` на сервере: `<время>.db` и
`<время>.tar.gz`, распакованные в один каталог как `site.db`, `uploads/`, `files/`) — прогони и на ней.
Миграция модуля меняет существующие данные (так сказано в `UPGRADE.md`) — проверь на копии и сами данные: что
обещает раздел `UPGRADE.md` (записи на месте, изображения открываются).

## 7. Итог человеку

Начни с главного: что обновлено (модуль: версии, что нового для сайта) и что всё проверено — тесты, миграции на
копии; что не запускалось и почему (нет Chrome — что поставить).

Затем:
- отклонения от `UPGRADE.md` и конфликты с правками сайта — что и почему;
- из эталона: что перенесено; новые возможности, которые можно добавить отдельной задачей;
- новые мажорные версии, которые не ставились;
- **на сервере** — по разделу «Развёртывание» `AGENTS.md` сайта: `make build GOOS=linux GOARCH=amd64`, новый бинарник
  рядом, `systemctl stop site`, замена, `systemctl start site-migrate` (сначала снимок БД, потом миграции),
  `systemctl start site`, `curl -s 127.0.0.1:8080/healthz` — новая версия и `pending: 0`; затем, если нужна,
  повторная обработка `site reprocess-images -below <N>` (сервер может работать; прерванную — запустить снова).
  Если миграция меняет данные — перед ней ещё `site backup`, и сказать, как откатиться (восстановление из снимка —
  раздел «Резервные копии»).

В конце — один вопрос (`AskUserQuestion`), что сделать с веткой: есть `origin` и `gh` — «Отправить и открыть PR»;
всегда — «Слить в main» (`git switch main && git merge --ff-only <ветка>`) и «Оставить ветку». Без ответа ничего не
отправляй и не сливай.
