# create-site — новый сайт Keelkit

Сайт Keelkit — самостоятельное Go-приложение в своей папке. Он повторяет устройство эталона `reference/` монорепо
`github.com/keelkit/keelkit`, а отличается от него только тем, что задаёт `site.yaml`: типами контента, полями,
настройками, меню, языком. Общий код подключается модулями Keelkit как зависимости `go.mod`.

**Первый результат для человека — работающий сайт на `localhost`**, а не репозиторий и не ответы на технические
вопросы. Человек может ничего не знать о Go, модулях и git: всё техническое скилл решает сам значениями по
умолчанию и показывает их в плане одним списком — поправить можно в ответ на план или позже. GitHub, домен и
сервер — когда человек захочет опубликовать сайт, не раньше.

Принцип: **копируем эталон целиком и приводим его к спецификации**, а не пишем сайт с нуля. Конвенции — в
`AGENTS.md` эталона (после копирования — `AGENTS.md` нового сайта); этот скилл говорит, *что* менять и в каком
порядке, а *как* — показывает код эталона. Когда сомневаешься, как сделать, — найди то же в эталоне и сделай так же.

Аргументы: `$ARGUMENTS` — каталог сайта и, если есть, готовый `site.yaml`. Каталог не задан — текущий, если он
пуст (допустимы `.git` и `site.yaml`), иначе новая папка `./<site.name>`.

Справочники (читать по ходу работы, на шагах, где они названы):
- [references/content-types.md](references/content-types.md) — тип контента по спецификации: образец, таблицы,
  каждый тип поля и feature, адреса на сайте, админка, seed, тесты.
- [references/wiring.md](references/wiring.md) — все места, где тип, модуль, настройки и меню связаны с остальным
  кодом; что убрать вместе с типом эталона; адаптация общего кода (название, язык, модули).

## 0. Проверить окружение

Без этого сайт не собрать — нет чего-то, скажи человеку, что поставить (одной командой для его ОС), и остановись:
- `go version` — любой Go 1.21+: нужную версию (`toolchain` в `go.mod` эталона) он скачает сам (`GOTOOLCHAIN=auto`).
- `git --version`, `make --version`.
- Каталог сайта лежит **вне** монорепо Keelkit (если человек работает в его клоне): иначе каталог подхватит `go.work`
  монорепо, и сборка пойдёт на неопубликованном коде модулей.

Chrome нужен только браузерным тестам админки (`make e2e-browser`). Нет его — не останавливайся: в итоге скажи,
что эти тесты не запускались и что для них поставить.

## 1. Спецификация `site.yaml`

**Готовый `site.yaml` дан — вопросов нет.** Возьми его и дополни умолчаниями (ниже).

**Не дан — один вопрос** (`AskUserQuestion`): что за сайт. Варианты — готовые наборы разделов (свой ответ человек
введёт в «Другое»):
- **Блог** — страницы, посты с датой, обложкой и категорией, RSS (как `pages`, `posts`, `categories` эталона);
- **Сайт компании** — страницы из блоков, новости, команда блоком на странице (`pages`, `news` по образцу `posts`,
  `team` по образцу `people`), файлы;
- **Визитка** — только страницы из блоков (`pages`).

Название сайта, язык и разделы бери из ответа и разговора; чего там нет — умолчания. Поля и features каждого типа —
по таблицам [content-types.md](references/content-types.md). Не спрашивай о том, что следует из выбранного: `slug`
у типа со своим адресом, `seo` и `sitemap` у него же, `draft` у ленты.

**Умолчания** — без вопросов, все попадают в план:
- `site.name` — техническое имя латиницей через дефис (`my-blog`), название для людей — в настройки; язык — язык
  разговора с человеком.
- Настройки — набор эталона (название, описание, контакты, картинка для соцсетей, баннер cookies, коды вебмастеров,
  соцсети); меню — `[main, footer]`. Так и для готового `site.yaml` без `settings` и `menus`: настройки и меню
  предлагаются всегда (решение владельца Keelkit) — допиши их в `site.yaml` и отметь в плане как добавленные.
  Человек в ответ на план отказался — сайт без них: название и описание — константами в коде, раздела «Настройки»
  или «Меню» в админке нет (см. [wiring.md](references/wiring.md), «Сайт без настроек или меню»).
- Модули: `images`, `richtext`, `auth` — всегда (на них стоят медиатека, блоки, админка); `files` (PDF, видео,
  SVG) — если о файлах шла речь или выбран сайт компании.
- Тип `pages` с полями `title` и `slug` обязателен (главная — slug `home`, адреса `/{slug}`): нет — добавь.
- Тип без своего адреса (без `slug`), записи которого никто не выводит, — блок-список на страницах: имя блока типа
  в `allow` поля `blocks` страниц (образец — `people`). У страниц нет поля `blocks` — выводи записи на главной.
- Путь Go-модуля — `site.name` (`my-blog`); это лишь имя внутри кода, к GitHub и домену оно не привязано.

Пиши `site.yaml` в стиле эталона: порядок `spec_version`, `site`, `modules`, `settings`, `menus`, `content`;
отступ 2 пробела; короткие комментарии там, где выбор не очевиден. `modules` — в порядке применения миграций,
как в эталоне (`images`, `files`, `richtext`, `auth`). Положи его в каталог сайта — проверка `make spec-validate`
после копирования эталона (шаг 2).

**План — одно сообщение человеку**, без вопроса в конце: разделы сайта и их адреса, разделы админки, что
добавлено к спецификации умолчаниями (настройки, меню, модули), папка сайта. Человек может поправить что угодно
ответом; не ждёт ответа — работай дальше.

## 2. Скопировать эталон

```sh
"${CLAUDE_SKILL_DIR}/scripts/fetch-reference.sh" <каталог сайта> <путь модуля>
```

Скрипт берёт `reference/` из монорепо на теге плагина `skills/v<версия>` (скилл и эталон одной версии), меняет
путь модуля во всех файлах, не трогает готовый `site.yaml` и печатает строку `reference: <тег> <коммит>` — сохрани
её для `AGENTS.md` сайта. `KEELKIT_REPO=<путь к клону монорепо>` берёт эталон из локального клона (разработка
скиллов, эвалы).

Сразу зафиксируй исходное состояние локальным git — он нужен, чтобы видеть отличия сайта от эталона и чтобы потом
работал `upgrade-site`; ни GitHub, ни аккаунт для этого не нужны: `git init -b main` (если репозитория нет),
`git add -A`, `git commit -m "Эталон Keelkit <тег>"`. `make spec-validate` — ошибки `site.yaml` исправь.

Прочитай `AGENTS.md` (это конвенции эталона, теперь — сайта), `cmd/site/server.go` и `db/schema.sql`
(итоговая схема БД эталона) — без них следующие шаги не сделать правильно.

## 3. Привести код к спецификации

Порядок важен: сначала схема БД, потом пакеты типов, потом связи, потом общий код — так компилятор и `sqlc`
находят пропущенное.

1. **Миграции.** У нового сайта нет истории: удали миграции эталона (`db/migrations/*.sql`, `embed.go` остаётся) и
   напиши новые с `00001` — итоговые схемы, без промежуточных шагов эталона. Порядок — по внешним ключам: таблица
   идёт после тех, на которые ссылается. Обычно: `00001_site_settings.sql` (если есть настройки; ссылается только на
   `images_files`), `00002_pages.sql`, `00003_menus.sql` (если есть меню: `menu_items.page_id` ссылается на
   `pages`), затем остальные типы — тип, на который ссылаются через `ref`, раньше ссылающегося (`categories` до
   `posts`). Образцы таблиц — `db/schema.sql` эталона (без `pages_legacy`, `users`/`sessions` — они у модуля
   `auth`); правила колонок — [content-types.md](references/content-types.md).
2. **Пакеты типов** `internal/content/<тип>/` — по образцу, выбранному в [content-types.md](references/content-types.md).
   Тип эталона, которого нет в спецификации, удали целиком; тип с другим именем — новый пакет по образцу
   (имя пакета = имя типа). Запись в `sqlc.yaml` на каждый пакет.
3. **Связи** — по чек-листу [wiring.md](references/wiring.md): маршруты, админка, дашборд, «где используется»
   изображение и файл, sitemap, RSS, меню, блоки-списки, `reservedSlugs`, списки в `cmd/site/spec_test.go`.
4. **Общий код** — [wiring.md](references/wiring.md): модули (нет `files` — убрать всё о файлах), настройки, меню,
   язык, название сайта и имена эталона в коде и вне его (`Makefile`, `static/style.css`). Общие пакеты остаются,
   даже если сейчас ими не пользуется ни один тип: `internal/blocks` без полей `blocks` (в нём Markdown-поле, превью,
   выбор картинок), `internal/seofields` без feature `seo` — раздел «Сайт без блоков, SEO или порядка» `wiring.md`.
5. **Seed** (`cmd/site/seed.go`): dev-данные каждого типа на языке сайта, правдоподобные для этого сайта (не
   «Lorem ipsum» и не тексты эталона о Keelkit): главная (`home`) и пара страниц, у ленты — больше 10 записей (вторая
   страница ленты), черновик и запись с датой в будущем, если есть такие features. Идемпотентно, как в эталоне.
6. `make generate`, затем `make schema` (снимок новой схемы в `db/schema.sql`), `go mod tidy` через
   `GOFLAGS=-tags=nodynamic` (или любую цель `make`, которая собирает код), если модуль убран.

## 4. Тесты

Сайт обязан быть проверен так же, как эталон. Тесты эталона — образец, а не мусор: адаптируй, а не удаляй.
Тесты эталона проверяют тексты его seed («Keelkit — эталонный сайт», категории «Go» и «Веб», заголовки страниц):
новый seed ломает почти все e2e. Сначала напиши seed, затем пройди `git grep` по прежним текстам seed в
`cmd/site/*_test.go` и замени ожидания; повторяющиеся тексты (название сайта, slug и заголовки страниц) — константами
в `seed.go`, тесты ссылаются на них.
- Контрактные тесты модулей (`images_test.go`, `files_test.go` если есть `files`, `richtext_test.go`, `auth_test.go`)
  и `backup_test.go`, `schema_test.go` — остаются, правятся только под новые типы (через какую страницу публикуется
  Markdown и т. п.).
- `spec_test.go` — остаётся целиком; списки в нём (`seoTypes`, `orderTypes`, карта блоков) — по спецификации.
- `migrations_test.go` — тесты миграций данных эталона (`TestMigrationPageContents`, `TestMigrationAuthOverSiteTables`)
  к новому сайту не относятся: удали их, хелпер `migrateTo` оставь, если пригодится, иначе удали (линтер).
- e2e на каждый тип: публичные страницы (`e2e_test.go`, `e2e_blog_test.go` — образцы) и раздел админки
  (`e2e_pages_admin_test.go`, `e2e_posts_admin_test.go`, `e2e_people_admin_test.go`): создание, каждая ошибка
  валидации (форма и `HX-Request`), публикация и черновик, удаление, 409 для используемого, SEO, sitemap/RSS.
- Браузерные тесты (`browser_test.go`): каждое JS-поведение админки, которое осталось на сайте; тест удалённого
  поведения — удалить, у нового типа с тем же поведением — тот же сценарий. Сценарии эталона завязаны на блоки
  страниц (`.block-form textarea`, `page_contents`) и на `people`; куда их переносить:

  | Тест эталона | На сайте |
  |---|---|
  | `TestBrowserPagePreviewAndSave` | форма страниц: у страниц без `blocks` — Markdown-поле `#<поле>` (`#body`), превью `#<поле>-preview`; без `draft` — одна кнопка «Сохранить» и её сообщение; таблица и тексты ошибок — из кода сайта |
  | `TestBrowserBlocks` | тип с полем `blocks`; нет такого — удалить |
  | `TestBrowserMediaUpload`, `TestBrowserSettingsAndCookieBanner`, `TestBrowserMenu` | как в эталоне (настройки и меню — если есть) |
  | `TestBrowserPostCover` | тип с полем `image` (`select[name="<поле>"]`) |
  | `TestBrowserSEOSnippet` | тип с feature `seo`; нет такого — удалить |
  | `TestBrowserMarkdownToolbar` | любое поле `richtext` или блок `text`: `#<поле>`, кнопки `.md-toolbar[aria-controls="<поле>"]` |
  | `TestBrowserPeopleOrder` | тип с feature `order`; нет такого — удалить |
  | `TestBrowserLivePreview` | тип с живым предпросмотром (`blocks` или `image` с `mobile`); на новой записи (`/admin/<тип>/new`) — ничего не сохраняется |
  | `TestBrowserMobileImage` | поле `image` с `mobile: true` (выбор телефона — `select[name="<поле>_mobile"]`) или блок `image`; нет ни того ни другого — удалить |

## 5. Документация

`AGENTS.md` сайта — это `AGENTS.md` эталона, приведённый к сайту:
- заголовок и вводный абзац — о сайте; убрать всё, что описывает эталон как образец для других сайтов;
- раздел «Версии»: плюс строка «Keelkit: плагин `keelkit` ≥ <версия из plugin.json>; создан create-site из эталона
  `<тег> <коммит>`» (строка из шага 1) — по ней `upgrade-site` поймёт, от какого эталона считать изменения;
- маршруты, типы контента, seed, тесты, структура — как на этом сайте; удалённые типы и модули — убрать;
- история эталона (номера его миграций, «до этапа 10.4», `pages_legacy`) — убрать: у сайта своя история.

Это самая долгая часть после тестов: `AGENTS.md` эталона — ~800 строк. Иди по разделам, а не по строкам:
- целиком убрать: раздел «Файлы» (нет `files`); абзацы об удалённых типах (`people`, «Команда», «Документы») и
  блоках (`file`, блок-список); тесты миграций данных (`migrations_test.go`); строки «Структуры» и «Тестов» об
  удалённых файлах;
- переписать под сайт: «Маршруты» (разделы и адреса типов), «Тип контента» (образцы — типы этого сайта, seed),
  «Меню» (seed, `menuSections`), «Настройки» (поля из `site.yaml`), `/healthz` (номер версии схемы сайта), номера
  миграций в тексте — новые;
- оставить как есть: общее устройство (команды, конфигурация, бинарник, резервные копии, развёртывание, Docker,
  изображения, шаблоны, админка, черновик-копия, живой предпросмотр, поле-список, SEO) — это конвенции и сайта;
  убранное общее (блоки без полей `blocks`, `seofields` без `seo`) — одной строкой «пакет есть, на сайте не используется».
Признак готовности: `grep -n -i -E '<удалённые типы>|filelib|seedfiles|legacy|этап|эталон'` находит только
намеренное (ссылки на эталон как образец).
`site.yaml` — комментарии о том, где поле выводится, если это не очевидно.

## 6. Проверка

Всё через `make`, в каталоге сайта; каждая ошибка — исправить и повторить, а не обойти:

```sh
make generate && make schema
make lint
make test            # unit, e2e, контрактные тесты модулей, site.yaml ↔ код
make e2e-browser     # если есть Chrome
make spec-validate
"${CLAUDE_SKILL_DIR}/scripts/check-site.sh" .     # структура и конвенции, имя образа Docker
git add -A && git commit -m "Сайт <name> по site.yaml" && make generate-check   # генерация ничего не меняет
```

Затем живая проверка: `make dev` в фоне, `curl -s localhost:9090/healthz` (`pending` у всех схем — 0), главная,
страница каждого типа со своим адресом, `/admin/login` (вход `admin@example.com` / `adminadmin`), `/sitemap.xml`
и `/rss.xml`, если они есть; затем остановить сервер.

## 7. Итог человеку

Начни с того, как открыть сайт — это главное: `cd <папка> && make dev`, сайт — `http://localhost:9090`, админка —
`http://localhost:9090/admin` (`admin@example.com` / `adminadmin`); что там уже есть (разделы, примеры записей).
Затем коротко: что в сайте (разделы, адреса, разделы админки), что взято умолчаниями и какие решения принял сам
(образцы, поля без образца в эталоне; отклонений от спецификации быть не должно, а если есть — почему), результаты
проверок (не запускались браузерные тесты — сказать, что поставить).

В конце — «когда захотите опубликовать»: код — в свой репозиторий (`git remote add origin …`, `git push`), сайт —
на сервер (раздел «Развёртывание» в `AGENTS.md` сайта), первый пользователь — `make user-create` на сервере.
