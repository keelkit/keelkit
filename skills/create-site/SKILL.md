# create-site — новый сайт Keelkit

Сайт Keelkit — самостоятельное Go-приложение в своей папке. Он повторяет устройство эталона `reference/` монорепо
`github.com/keelkit/keelkit`, а отличается от него только тем, что задаёт `site.yaml`: типами контента, полями,
настройками, меню, языком. Общий код подключается модулями Keelkit как зависимости `go.mod`.

**Сайт строится по шагам, от простого к сложному.** Сначала — интервью и план (`PLAN.md` с чекбоксами), затем
по одному шагу плана за сессию: человек проверяет результат, очищает контекст и просит следующий шаг. Сайт может
строиться неделю — это нормально; планы по ходу меняются, и план меняется вместе с ними.

**Расход токенов контролирует человек.** Один вызов скилла — одна фаза: план или один шаг, затем остановка.
Не запускай подагентов, фоновых агентов и `claude -p`, не делай следующий шаг без просьбы человека. Читай только
то, что нужно шагу: нужный раздел справочника, образец в эталоне, а не всё подряд; длинный вывод команд — хвостом
(`2>&1 | tail -40`).

Человек может ничего не знать о Go, модулях и git: техническое скилл решает сам значениями по умолчанию и
показывает их в плане. GitHub, домен и сервер — когда человек захочет опубликовать сайт, не раньше.

Принцип: **копируем эталон и приводим его к спецификации**, а не пишем сайт с нуля. Конвенции — в `AGENTS.md`
эталона (после копирования — `AGENTS.md` сайта); этот скилл говорит, *что* менять и в каком порядке, а *как* —
показывает код эталона. Когда сомневаешься, как сделать, — найди то же в эталоне и сделай так же.

Аргументы: `$ARGUMENTS` — каталог сайта и, если есть, готовый `site.yaml`. Каталог не задан — текущий, если он
пуст или в нём уже есть `PLAN.md` (допустимы `.git`, `site.yaml`, `PLAN.md`), иначе новая папка `./<site.name>`.

**Какая фаза:** в каталоге нет `PLAN.md` — фаза «План» (шаги 0–2 ниже). Есть — фаза «Шаг плана» (раздел «Шаг
плана»): первый шаг с неотмеченными чекбоксами.

Справочники (читать на шагах, где они названы, и только нужный раздел):
- [references/interview.md](references/interview.md) — интервью: как спрашивать, темы, когда закончить.
- [references/site-plan.md](references/site-plan.md) — `PLAN.md`: размер шага, формат, типовые шаги.
- [references/content-types.md](references/content-types.md) — тип контента по спецификации: образец, таблицы,
  каждый тип поля и feature, адреса на сайте, админка, seed, тесты.
- [references/wiring.md](references/wiring.md) — все места, где тип, модуль, настройки и меню связаны с остальным
  кодом; что убрать вместе с типом эталона; адаптация общего кода (название, язык, модули).

# Фаза «План»

## 0. Проверить окружение

Без этого сайт не собрать — нет чего-то, скажи человеку, что поставить (одной командой для его ОС), и остановись:
- `go version` — любой Go 1.21+: нужную версию (`toolchain` в `go.mod` эталона) он скачает сам (`GOTOOLCHAIN=auto`).
- `git --version`, `make --version`.
- Каталог сайта лежит **вне** монорепо Keelkit (если человек работает в его клоне): иначе каталог подхватит `go.work`
  монорепо, и сборка пойдёт на неопубликованном коде модулей.

Chrome нужен только браузерным тестам админки (`make e2e-browser`). Нет его — не останавливайся: скажи, что эти
тесты не будут запускаться и что для них поставить.

## 1. Спецификация `site.yaml`

**Готовый `site.yaml` дан — вопросов о нём нет.** Возьми его и дополни умолчаниями (ниже).

**Не дан — интервью** по [references/interview.md](references/interview.md): вопросы о содержании сайта по одной
теме, пока не станет ясно, какие нужны разделы и что в их записях; техническое — умолчаниями (ниже). Первый
вопрос (`AskUserQuestion`) — что за сайт. Варианты — готовые наборы разделов (свой ответ человек введёт в
«Другое»); набор — начало интервью, а не его итог:
- **Блог** — страницы, посты с датой, обложкой и категорией, RSS (как `pages`, `posts`, `categories` эталона);
- **Сайт компании** — страницы из блоков, новости, команда блоком на странице (`pages`, `news` по образцу `posts`,
  `team` по образцу `people`), файлы;
- **Визитка** — только страницы из блоков (`pages`).

Название сайта, язык и разделы бери из ответов; чего там нет — умолчания. Поля и features каждого типа — по
таблицам [content-types.md](references/content-types.md). Не спрашивай о том, что следует из выбранного: `slug`
у типа со своим адресом, `seo` и `sitemap` у него же, `draft` у ленты.

**Умолчания** — без вопросов, все попадают в план:
- `site.name` — техническое имя латиницей через дефис (`my-blog`), название для людей — в настройки; язык — язык
  разговора с человеком.
- Настройки — набор эталона (название, описание, контакты, картинка для соцсетей, баннер cookies, коды вебмастеров,
  соцсети); меню — `[main, footer]`. Так и для готового `site.yaml` без `settings` и `menus`: настройки и меню
  предлагаются всегда (решение владельца Keelkit) — допиши их в `site.yaml` и отметь в плане как добавленные.
  Человек отказался — сайт без них: название и описание — константами в коде, раздела «Настройки» или «Меню» в
  админке нет (см. [wiring.md](references/wiring.md), «Сайт без настроек или меню»).
- Модули: `images`, `richtext`, `auth` — всегда (на них стоят медиатека, блоки, админка); `files` (PDF, видео,
  SVG) — если о файлах шла речь или выбран сайт компании.
- Тип `pages` с полями `title` и `slug` обязателен (главная — slug `home`, адреса `/{slug}`): нет — добавь.
- Тип без своего адреса (без `slug`), записи которого никто не выводит, — блок-список на страницах: имя блока типа
  в `allow` поля `blocks` страниц (образец — `people`). У страниц нет поля `blocks` — выводи записи на главной.
- Путь Go-модуля — `site.name` (`my-blog`); это лишь имя внутри кода, к GitHub и домену оно не привязано.

Пиши `site.yaml` в стиле эталона: порядок `spec_version`, `site`, `modules`, `settings`, `menus`, `content`;
отступ 2 пробела; короткие комментарии там, где выбор не очевиден. `modules` — в порядке применения миграций,
как в эталоне (`images`, `files`, `richtext`, `auth`). Проверка `make spec-validate` — на шаге «Эталон запущен».

## 2. План `PLAN.md`

Разбей сайт на шаги по [references/site-plan.md](references/site-plan.md): типовые шаги, по шагу на тип контента,
у каждого — «Как проверить». Положи `site.yaml` и `PLAN.md` в каталог сайта, `git init -b main` (если
репозитория нет), `git add -A`, `git commit -m "План сайта <name>"`.

**Сообщение человеку:** разделы сайта и их адреса, разделы админки, что добавлено умолчаниями (настройки, меню,
модули), что отложено («позже»), список шагов плана одной строкой каждый, папка сайта.
- После интервью — один вопрос в конце: начинать ли по плану или поправить (план подытоживает ответы человека).
  Поправка — исправь `site.yaml` и `PLAN.md`, закоммить, покажи снова.
- Готовый `site.yaml` — без вопроса.

В конце: «Очистите контекст (`/clear`) и скажите `/create-site` в папке сайта — сделаю шаг 1». Остановись.

# Фаза «Шаг плана»

Один вызов — один шаг. Прочитай `PLAN.md` и `site.yaml`; шаг — первый с неотмеченными чекбоксами. Человек
назвал другой шаг или попросил изменить план — сделай, как он сказал (правка плана — тоже коммит).

1. **Оцени размер** по [site-plan.md](references/site-plan.md), «Размер шага». Велик — разбей его в `PLAN.md` на
   части, закоммить план и делай первую часть.
2. **Сделай шаг** — по разделу ниже для этого вида шага. Читай только нужное: `AGENTS.md` сайта загружен сам;
   образец — файлы эталона в сайте или в коммите «Эталон Keelkit» (`git show <коммит>:<путь>` — удалённое на
   шаге «Основа сайта» лежит там).
3. **Seed** (`cmd/site/seed.go`) — тестовое наполнение того, что появилось на шаге: на языке сайта, правдоподобное
   для этого сайта (не «Lorem ipsum» и не тексты эталона о Keelkit). Идемпотентно, как в эталоне. Именно по нему
   человек проверяет шаг.
4. **Тесты** нового (раздел «Тесты» ниже).
5. **Проверки шага:**
   ```sh
   make generate && make schema     # если менялись запросы, templ или миграции
   make lint
   make test
   make e2e-browser                 # только если шаг менял JS-поведение админки (и есть Chrome)
   ```
   Ошибка — исправь и повтори, а не обойди. Затем живо: `make dev` в фоне, `curl` адресов из «Как проверить»
   (`/healthz` — `pending` у всех схем 0), остановить сервер.
6. **Отметь** чекбоксы шага в `PLAN.md`; поменялось по ходу — поправь пункты и «Как проверить».
   `git add -A && git commit -m "Шаг N: <название>"`, затем `make generate-check`.
7. **Итог человеку** — коротко: что сделано; **как проверить** — `cd <папка> && make dev` и блок «Как проверить»
   шага (адреса, что видно из seed, что нажать в админке; вход `admin@example.com` / `adminadmin`); решения,
   принятые самостоятельно; что не запускалось (браузерные тесты без Chrome). В конце — следующий шаг плана и
   «очистите контекст и скажите `/create-site`». Остановись.

## Шаг «Эталон запущен»

```sh
"${CLAUDE_SKILL_DIR}/scripts/fetch-reference.sh" <каталог сайта> <путь модуля>
```

Скрипт берёт `reference/` из монорепо на теге плагина `skills/v<версия>` (скилл и эталон одной версии), меняет
путь модуля во всех файлах, не трогает `site.yaml` и `PLAN.md` и печатает строку `reference: <тег> <коммит>` —
запиши её в `PLAN.md` под заголовком (её же — в `AGENTS.md` сайта на шаге «Документация»).
`KEELKIT_REPO=<путь к клону монорепо>` берёт эталон из локального клона (разработка скиллов, эвалы).

Коммит `git add -A && git commit -m "Эталон Keelkit <тег>"` — до любых правок: от него видны отличия сайта
от эталона, и по нему работает `upgrade-site`. `make spec-validate` — ошибки `site.yaml` исправь. Seed и тесты
на этом шаге — эталона; проверка — `make dev`, эталон на `:9090`.

## Шаг «Основа сайта»

Прочитай `cmd/site/server.go` и `db/schema.sql` (итоговая схема БД эталона). Порядок: схема БД → пакеты →
связи → общий код — так компилятор и `sqlc` находят пропущенное.

1. **Миграции.** У нового сайта нет истории: удали миграции эталона (`db/migrations/*.sql`, `embed.go` остаётся) и
   напиши новые с `00001` — итоговые схемы, без промежуточных шагов эталона: `00001_site_settings.sql` (если есть
   настройки; ссылается только на `images_files`), `00002_pages.sql`, `00003_menus.sql` (если есть меню:
   `menu_items.page_id` ссылается на `pages`). Образцы таблиц — `db/schema.sql` эталона (без `pages_legacy`,
   `users`/`sessions` — они у модуля `auth`).
2. **Типы эталона, кроме `pages`, — удали** целиком (пакеты, записи `sqlc.yaml`, связи по [wiring.md](references/wiring.md)):
   они вернутся своими шагами по образцу из коммита эталона. `pages` — приведи к `site.yaml`.
3. **Общий код** — [wiring.md](references/wiring.md): модули (нет `files` в `site.yaml` — убрать всё о файлах),
   настройки, меню, язык, название сайта и имена эталона в коде и вне его (`Makefile`, `static/style.css`). Общие
   пакеты остаются, даже если ими пока никто не пользуется (`internal/blocks`, `internal/seofields`) — раздел
   «Сайт без блоков, SEO или порядка» `wiring.md`.
4. Seed — главная (`home`) и пара страниц, настройки, меню. `go mod tidy` с `GOWORK=off GOFLAGS=-tags=nodynamic`,
   если модуль убран.
5. Тесты удалённых типов — удали (вернутся с типами), остальные — под новый seed (раздел «Тесты»). В начало
   `AGENTS.md` сайта — строка: «Сайт в разработке по `PLAN.md`; разделы об устройстве эталона приводятся к сайту
   на шаге „Документация“».

## Шаг «Раздел <тип>»

По [content-types.md](references/content-types.md): образец, таблицы, поля, features, админка.
1. Миграция — следующий номер; таблица идёт после тех, на которые ссылается (`ref`).
2. Пакет `internal/content/<тип>/` по образцу (имя пакета = имя типа; образец удалён — из коммита эталона),
   запись в `sqlc.yaml`.
3. Связи — по чек-листу [wiring.md](references/wiring.md), «Тип контента: все места»: маршруты, админка, дашборд,
   «где используется» изображение и файл, sitemap, RSS, меню, блоки-списки, `reservedSlugs`, списки в
   `cmd/site/spec_test.go`.
4. Seed: у ленты — больше 10 записей (вторая страница ленты), черновик и запись с датой в будущем, если есть такие
   features.

## Шаги «Файлы», «Оформление» и прочие

«Файлы» — модуль `files` по [wiring.md](references/wiring.md), «Модули», и по эталону (`internal/filelib`, блок
`file`). «Оформление» — `static/style.css` и `internal/web` сайта; вендоренные шрифты — по `AGENTS.md` сайта.
Шаг без раздела здесь — по эталону и `AGENTS.md` сайта, тем же порядком 1–7.

## Шаг «Документация и итоговая проверка»

`AGENTS.md` сайта — это `AGENTS.md` эталона, приведённый к сайту:
- заголовок и вводный абзац — о сайте; убрать всё, что описывает эталон как образец, и строку «в разработке»;
- раздел «Версии»: плюс строка «Keelkit: плагин `keelkit` ≥ <версия из plugin.json>; создан create-site из эталона
  `<тег> <коммит>`» (строка из `PLAN.md`) — по ней `upgrade-site` поймёт, от какого эталона считать изменения;
- маршруты, типы контента, seed, тесты, структура — как на этом сайте; удалённые типы и модули — убрать;
- история эталона (номера его миграций, «до этапа 10.4», `pages_legacy`) — убрать: у сайта своя история.

Иди по разделам, а не по строкам (`AGENTS.md` эталона — ~800 строк; большой — раздели шаг на две сессии):
- целиком убрать: раздел «Файлы» (нет `files`); абзацы об удалённых типах (`people`, «Команда», «Документы») и
  блоках (`file`, блок-список); тесты миграций данных; строки «Структуры» и «Тестов» об удалённых файлах;
- переписать под сайт: «Маршруты», «Тип контента» (образцы — типы этого сайта, seed), «Меню» (seed,
  `menuSections`), «Настройки» (поля из `site.yaml`), `/healthz` (номер версии схемы сайта), номера миграций;
- оставить как есть: общее устройство (команды, конфигурация, бинарник, резервные копии, развёртывание, Docker,
  изображения, шаблоны, админка, черновик-копия, живой предпросмотр, поле-список, SEO) — это конвенции и сайта;
  убранное общее (блоки без полей `blocks`, `seofields` без `seo`) — одной строкой «пакет есть, на сайте не используется».
Признак готовности: `grep -n -i -E '<удалённые типы>|filelib|seedfiles|legacy|этап|эталон'` находит только
намеренное (ссылки на эталон как образец).

Итоговая проверка — всё, а не только проверки шага:
```sh
make generate && make schema && make lint && make test && make e2e-browser && make spec-validate
"${CLAUDE_SKILL_DIR}/scripts/check-site.sh" .     # структура и конвенции, имя образа Docker
```
В итоге человеку — ещё «когда захотите опубликовать»: код — в свой репозиторий (`git remote add origin …`,
`git push`), сайт — на сервер (раздел «Развёртывание» в `AGENTS.md` сайта), первый пользователь —
`make user-create` на сервере.

## Тесты

Сайт обязан быть проверен так же, как эталон. Тесты эталона — образец, а не мусор: адаптируй, а не удаляй.
Тесты эталона проверяют тексты его seed («Keelkit — эталонный сайт», категории «Go» и «Веб», заголовки страниц):
новый seed ломает их. После seed пройди `git grep` по прежним текстам seed в `cmd/site/*_test.go` и замени
ожидания; повторяющиеся тексты (название сайта, slug и заголовки страниц) — константами в `seed.go`, тесты
ссылаются на них.
- Контрактные тесты модулей (`images_test.go`, `files_test.go` если есть `files`, `richtext_test.go`, `auth_test.go`)
  и `backup_test.go`, `schema_test.go` — остаются, правятся только под новые типы (через какую страницу публикуется
  Markdown и т. п.).
- `spec_test.go` — остаётся целиком; списки в нём (`seoTypes`, `orderTypes`, карта блоков) — по спецификации.
- `migrations_test.go` — тесты миграций данных эталона (`TestMigrationPageContents`, `TestMigrationAuthOverSiteTables`)
  к новому сайту не относятся: удали их, хелпер `migrateTo` оставь, если пригодится, иначе удали (линтер).
