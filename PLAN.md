# PLAN.md — план первого этапа Keelkit

Пошаговый план по разделу «Первый этап» из `AGENTS.md`. Отмечайте прогресс чекбоксами.

**Правило плана:** после каждого этапа сервис находится в рабочем состоянии —
его можно запустить одной командой и увидеть результат в браузере, в JSON или в сгенерированной HTML-странице.
Этап не считается завершённым, пока не пройден его раздел «Проверка».

**Общие соглашения для проверок** (появляются на этапе 0–2 и дальше не меняются):
- `make dev` — применить миграции, залить seed, запустить сайт на `http://localhost:9090`.
- `make reset` — удалить локальную dev-БД и загрузки (`reference/data/`), чтобы начать с нуля (сервер перед этим остановлен).
- `GET /healthz` — JSON о состоянии: версия сборки, версии схем БД (сайт и каждый модуль), число непримененных миграций.
- Seed идемпотентен: повторный `make seed` не создаёт дублей. Seed-данные только для dev, в проде не запускаются.

## Этап 4. Авторизация и оболочка админки — ✅ готово

Цель: вход в админку одним пользователем («простой режим»).

Сделано: `golang.org/x/crypto` v0.57.0 (argon2id), `golang.org/x/term` v0.46.0 (ввод пароля без эха; уже был в графе через x/crypto).
Сессия — случайный токен в cookie `session` (14 дней), в БД только его SHA-256; CSRF-токен хранится в строке сессии
и передаётся полем `csrf_token` или заголовком `X-CSRF-Token` (`hx-headers` на `<body>` для htmx). Форма входа до сессии
защищена double submit cookie `admin_csrf`; весь `/admin` дополнительно обёрнут в `http.CrossOriginProtection`.
Ограничение входа — в памяти процесса, по email: 5 неудач за 15 минут → блокировка до конца окна (429 и `Retry-After`).
Для неизвестного email пароль сверяется с фиктивным хешем — время ответа не выдаёт, есть ли пользователь.
Одновременно считается не больше двух хешей argon2id (по 64 МиБ). Хеш со старыми параметрами пересчитывается при входе.
`Secure` у cookie управляется `COOKIE_SECURE` (по умолчанию `true`; `make run`/`make dev` передают `false`).
Попутно: `govulncheck` сообщает о GO-2026-5932 (`golang.org/x/crypto/openpgp`, исправления нет) — пакет не импортируется,
модуль x/crypto был в графе и раньше; код не затронут.

- [x] Миграция: `users` (одна таблица, поле роли зарезервировано на будущее), `sessions`
- [x] Хеширование паролей argon2id (`golang.org/x/crypto/argon2`, решение в `AGENTS.md`), cookie `HttpOnly`, `SameSite=Lax`, `Secure` вне dev
- [x] CSRF-защита форм, ограничение попыток входа
- [x] `internal/admin/`: вход, выход, оболочка (меню, дашборд со счётчиками контента)
- [x] Подкоманда `site user create` / `make user-create EMAIL=...` (пароль спрашивается интерактивно); смены пароля нет — кандидат в бэклог

## Этап 6. Модуль `images`: обработка и хранилище — ✅ готово

Цель: ядро модуля работает и даёт наглядный результат без сайта.

Сделано: `golang.org/x/image` v0.46.0, `github.com/gen2brain/webp` v0.6.4. Парсер EXIF — свой (`internal/exif`,
решение в `AGENTS.md`), с fuzz-тестом. Публичный API: `Process`, `Result`/`Original`/`Variant`, `Result.Save`,
`Storage`, `DiskStorage` (через `os.Root`, атомарная запись temp+rename), ошибки `ErrTooLarge`, `ErrTooManyPixels`,
`ErrUnsupportedFormat`, `ErrInvalidImage`, `ErrNotFound`, константы `ProfileVersion`, `MaxBytes`, `MaxPixels`.
Решения по ходу:
- если оригинал меньше 2400 px в ширину, добавляется вариант его собственной ширины (800 px → 480 и 800), иначе у маленьких
  картинок не было бы ни одного варианта; шире оригинала вариантов нет;
- масштабирование в сохранённой ориентации, поворот — уже маленького варианта; большие уменьшения — сначала
  целочисленным усреднением блоков, потом Catmull-Rom (как в libvips): фото 40 Мп — ~1,3 с и ~410 МБ RSS вместо 780 МБ;
- прозрачность: WebP сохраняет альфа-канал, JPEG — на белом фоне; ICC-профили не переносятся (кандидат на профиль v2);
- оригинал хранится побайтно, с EXIF и GPS, поэтому публично отдаваться не должен (учесть в handler на этапе 7);
- `gen2brain/webp` с v0.6 — не wazero, а libwebp, транслированная в чистый Go (wasm2go); без CGO по-прежнему.
  Если в системе есть libwebp, библиотека подгружает её через purego; входные WebP поэтому декодирует
  `x/image/webp` (чистый Go), а системная libwebp видит только наши пиксели при кодировании.
  Тег `nodynamic` отключает подгрузку — на этапе 8 решено собирать с ним (`GOFLAGS` в `Makefile`);
- testdata генерирует `TestGenerateTestdata` (`go test -run TestGenerateTestdata -gen`), ориентации — по таблице из
  определения тега, а не через код модуля; `magick -auto-orient` независимо подтверждает все 8; `photo.heic` — через `sips`.

- [x] `modules/images/go.mod`, публичный API минимален, остальное в `internal/`
- [x] Декодирование JPEG, PNG, WebP; отказ для HEIC и прочих форматов с понятной ошибкой
- [x] Лимиты: 20 МБ и 40 мегапикселей — размеры проверяются по заголовку **до** полного декодирования
- [x] Ориентация EXIF применяется, затем EXIF удаляется (свой минимальный парсер: JPEG APP1, PNG eXIf, WebP EXIF)
- [x] Профиль v1: ширины 480/960/1600/2400 без увеличения, WebP q=80 (`gen2brain/webp`), JPEG q=82, ресайз `x/image/draw`
- [x] Интерфейс `Storage` + реализация на локальном диске; оригинал сохраняется всегда
- [x] `testdata/`: фото с каждой из 8 ориентаций EXIF, PNG с прозрачностью, маленькое изображение (без увеличения), «бомба» с огромными размерами в заголовке

- ограничение одновременных обработок — в сервисе модуля (`Config.MaxConcurrent`, по умолчанию 2), общее для загрузок
  и повторной обработки одного процесса; `make reprocess-images` — отдельный процесс со своим лимитом;
- `Reprocess(below)` с `below > ProfileVersion` равносилен `ProfileVersion` — иначе повторный запуск не был бы холостым;
- удаление файлов — через таблицу `images_trash` в той же транзакции; тест прерывает повторную обработку перед каждой
  записью по очереди и после каждого прерывания проверяет, что все варианты отдаются;
- `Handler` не читает БД: вариант отдаётся, пока его файл есть в хранилище; путь проверяется регулярным выражением,
  под которое оригинал не подходит;
- исходное имя файла хранится (`Image.Name`, без каталогов и управляющих символов) — для админки.

## Этап 8.5. Страницы из блоков и черновик-копия — ✅ готово

Цель: редактор собирает страницу из готовых блоков (текст, изображение, изображение + текст, цитата) вместо одного
Markdown-текста; вёрстку не сломать, картинки — из медиатеки с адаптивными размерами. Правки опубликованной страницы
не видны на сайте до нажатия «Опубликовать».

Образец подхода — сайт на Astro (`~/scripts/datum/astro/mrdn-new`: `src/cms/blocks.ts`, `src/pages/admin/works/[id].astro`).
Берём идею, не реализацию: там клиентский редактор на ~3000 строк TS, у нас — серверные фрагменты форм на templ + htmx.

Решения (приняты человеком, записаны в «Принятые решения» `AGENTS.md`):
- **Спецификация:** тип поля `blocks` со списком имён — `body: { type: blocks, allow: [text, image, image_text, quote] }`.
  Поля блоков в спецификации не описываются: набор блоков — дизайн сайта, живёт в коде. Валидатор: имена по
  `^[a-z][a-z0-9_]*$`, список непустой и без повторов, `allow` — только у `blocks` (и обязателен у него).
  Изменение схемы v1 добавочное: старые `site.yaml` остаются валидными. Что каждый блок из `allow` есть в коде,
  проверяет тест сайта (позже — `check-drift`).
- **Хранение:** блоки — JSON-массив в колонке (`CHECK (json_valid(blocks))`); порядок сохраняется атомарно, копия
  черновика — копия колонки. Ссылки на картинки — таблица `page_images(page_id, image_id REFERENCES images_files(id))`,
  перезаписывается в той же транзакции: используемую картинку не удалить, медиатека показывает, где она используется.
- **Черновик — отдельная копия:** `pages` — только идентичность; содержимое — `page_contents(page_id, kind IN ('draft',
  'published'), title, slug, blocks)`, `UNIQUE (page_id, kind)`. «Сохранить» пишет черновик, «Опубликовать» копирует его
  в опубликованную версию одной транзакцией, «Снять с публикации» удаляет опубликованную копию. slug — часть версии:
  адрес меняется при публикации (редиректы со старых адресов — этап 10, готово). Заменяет флажок `draft` (миграция 00004).
- **Код блоков:** один пакет `internal/blocks/`; страницы и посты его используют. Вынос механизма в модуль — после второго сайта.
- **Посты (этап 9):** тоже блоки и та же модель черновика; отдельный синтаксис картинок в Markdown не нужен.

Решения по ходу:
- старые колонки `pages` не удаляются, а остаются в переименованной таблице `pages_legacy` (у `title`/`slug` ограничения
  `NOT NULL`/`CHECK`/`UNIQUE` — новые страницы туда не записать); `DROP TABLE pages_legacy` — следующей миграцией;
- `page_images` — по копии (`page_id, kind, image_id`), каскадом от `page_contents`: опубликованная копия держит свои
  картинки, пока не снята с публикации; скрытые блоки тоже держат;
- блок неизвестного типа в админке не теряется (`blocks.Unknown`, сохраняется как есть), на сайт не выводится;
- кнопки блоков (↑/↓, «Скрыть», «Удалить блок», «Добавить блок» без JS) — submit всей формы с `action`; сервер
  возвращает форму изменённой без сохранения; через htmx «Добавить блок» получает только фрагмент блока;
- описание страницы (`meta description`) — `blocks.Summary`; новая страница — с одним пустым блоком `text`;
- опубликованная главная не меняет slug (иначе сайт открывался бы заглушкой).

## Этап 10.5. Доработки движка для реальных сайтов — ✅ готово

Цель: закрыть то, чего эталону не хватает для настоящего сайта компании: повторяющиеся данные внутри записей,
файлы помимо картинок, редактируемые контакты и меню, SEO записей вручную. Список собран на прототипе админки
реального сайта: в эталоне каждая возможность появляется в общем виде, без привязки к конкретному сайту.

Как работаем:
- Как обычно, сначала `reference/` и `AGENTS.md`; сайты, которые ждут этих возможностей, собираются после этапа.
- Каждая возможность в `reference/` — с образцом в seed и e2e-тестом, как остальные.

Решения, которые принимает человек до начала соответствующей части:
- **Спецификация.** Нужны новые возможности схемы: список элементов в поле, файл, раздел настроек, меню.
  Изменение схемы — только с подтверждением (новый тип поля или `spec_version: 2`).
- **Файлы.** Модуль `modules/files` или код сайта; как принимать SVG (очистка или только как вложение);
  лимит размера (сканы PDF бывают под 20 МБ).

Решения по ходу:
- списки внутри блока — тем же механизмом, что блоки: элементы с id, кнопки — submit с `action` (`item-up:<блок>:<элемент>`…),
  без JavaScript и с htmx; общий код — `internal/blocks/items.go`, новому блоку со списком нужны только поля элемента;
- галерея на сайте — лента на CSS scroll-snap без JavaScript (слайд 85% колонки, один слайд — во всю);
- в seed галерея «О проекте» не использует `small.jpg`: на нём тесты проверяют удаление свободного изображения;
- лид и анонс — простой текст (`type: text`), без Markdown; ручной анонс выводится целиком (без обрезки) в ленте, RSS
  и `meta description`; alt обложки без обложки не сохраняется, пустой — обложка декоративная; `og:image:alt` — alt обложки;
- SEO записи — сначала обычные поля `seo_*` в `site.yaml`, затем (решение о схеме ниже) feature `seo`; поля — часть
  копии (публикуются вместе с записью); SEO-заголовок — весь `<title>`, без названия сайта; SEO-описание меняет только
  `<head>`, анонс в ленте и RSS остаётся своим; раздел формы свёрнут, превью обновляется при любом вводе в форме.
- настройки — одна запись без черновика, сразу на сайте; баннер cookies — уведомление с «Понятно» (форма `POST
  /cookie-notice`, без JavaScript — 303 обратно, с htmx — баннер исчезает), cookie на год; коды подтверждения —
  мета-тегами на каждой странице, вставленный целиком мета-тег сводится к коду; картинка по умолчанию — `og:image`
  страниц без своей;
- типографика — после санитайзера, по тексту HTML (`x/net/html`, прямая зависимость той же версии, что у bluemonday):
  только пробелы → U+00A0, символы (кавычки, тире) не заменяются; код не трогается; описания и RSS — без неё.
- поле-список записи — `internal/listfield`, общий с элементами блоков код (id, порядок, `Apply`); кнопки —
  `list-<op>:<поле>:<элемент>`, хранение — JSON-массив в колонке; элемент со всеми пустыми полями при сохранении
  отбрасывается (пустой элемент галереи, наоборот, ошибка: у неё обязательная картинка);
- панель Markdown — свой `static/editor.js` (без библиотек), надстройка над textarea; вставка через
  `execCommand('insertText')` ради Ctrl+Z; браузерный тест — `TestBrowserMarkdownToolbar`;
- схема спецификации (решение человека): дополняем `spec_version: 1` (`spec v0.3.0`), прежние `site.yaml` валидны,
  кроме полей `seo_*`; `spec_version: 2` остаётся за мультиязычностью. `settings: { fields }` — запись настроек с
  полями как у типа (без `slug` и `blocks`); `menus: [main, footer]` — только имена, устройство пунктов — код сайта;
  `{ type: list, fields: {…} }` — список в поле записи, поля элемента задаёт спецификация (без вложенных `list`,
  `blocks`, `slug`; `id` элемента служебный); feature `seo` вместо полей `seo_*` (только у типа с `slug`).
- меню (решение человека) — данные, а не вид: движок отдаёт дерево `web.Link` с адресами, вывод — шаблон сайта.

  меню), адрес — по текущему slug, пустое название — заголовок страницы; снятая с публикации страница скрывает пункт.
  Пункт — страница, свой адрес или раздел из кода (подпункты из записей — флажком, у блога — категории с постами);
  вложенность вручную — один уровень; черновика нет, как у настроек.

  отложены до потребности сайта.

## Этап 10.6. Редактор записи с живым предпросмотром — ✅ готово

Цель: страница редактирования записи с блоками делится на две части — слева форма (блоки и поля), справа
предпросмотр: запись в шаблоне сайта, обновляется по мере ввода, без сохранения и без отдельной вкладки.

Как работаем:
- Код сайта, не модуль (принцип 2: админка — вёрстка сайта). Общая часть — `internal/admin` и `static/`,
  в каждом типе с блоками (pages, posts) — маршрут и короткий хендлер; `add-section` потом повторяет их для новых типов.
- Предпросмотр строится из **несохранённой формы**, а не из черновика: автосохранения нет, «Сохранить» остаётся
  явным действием (модель черновика-копии с этапа 8.5 не меняется). Основа уже есть — `viewData(ctx, f)` собирает
  запись из присланной формы, так работает превью SEO-сниппета.
- Без JavaScript форма работает как раньше, «Предпросмотр» открывает `/{id}/view`; панель предпросмотра — улучшение поверх.

Решения по ходу:
- маршрут без id — `POST /admin/<type>/live`: запись целиком в форме, id нужен только ссылке плашки, а плашки в живом
  предпросмотре нет (редактор рядом); так же работает для новой записи;
- связь блоков — по уже существующему якорю `block-<id>` (одинаков у формы блока и у блока на сайте), `data-block`
  не нужен; iframe того же происхождения (`srcdoc`), поэтому вместо `postMessage` — прямой доступ к его документу;
- следующие ответы заменяют только `<main>` в iframe: прокрутка не сбрасывается и картинки не мигают;
- превью Markdown у поля скрыто, пока предпросмотр рядом; во вкладках на узком экране (уже 64rem) — остаётся;
- скилла `add-section` ещё нет (этап 12): шаги для нового типа — в `reference/AGENTS.md`, «Живой предпросмотр».

- [x] `POST /admin/<type>/live` (`pages`, `posts`): `parseForm` → `viewData` → полная страница `View(v)` без плашки,
      noindex; ничего не пишет в БД (`cmd/site/e2e_live_test.go`: несохранённая правка в ответе, в БД её нет; новая
      запись; лид, дата и категория поста; 403 без CSRF)
- [x] Раскладка `admin.Live`: форма слева, `<iframe>` справа; граница перетаскивается (и стрелками), ширина
      запоминается (`localStorage`); уже 64rem — вкладки «Редактор / Предпросмотр»
- [x] Обновление: ввод в форме через 500 мс, устаревший запрос отменяется, прокрутка сохраняется; кнопка «Обновить»;
      после htmx-перерисовки формы или блока — тоже
- [x] Ширина устройства: «Компьютер 1440 / Телефон 390» (планшет был, убран: у сайта две ширины), масштаб под панель, подпись ширины и масштаба

## Этап 10.7. Своя картинка для телефона

Цель: у картинки записи может быть замена для узкого экрана (другой кадр той же сцены). Не задана — на телефоне
та же картинка, что на компьютере. Где: блоки «Изображение» и «Изображение с текстом», элементы галереи, обложка поста.

Как работаем:
- Код сайта, модуль `images` не меняется (принцип 2): у мобильной картинки свои варианты ширин, как у любой.
- Две ширины: компьютер и телефон. Граница — одна константа в `internal/web` (`MobileMedia`, экран уже 768 px);
  `media` в `<picture>` берёт её оттуда. Кнопки предпросмотра — «Компьютер» и «Телефон» (планшет убран в 10.6).
- Только файл: пропорции и фокус для телефона не задаются. Alt один на обе картинки — на них одно и то же.
- Вывод: `web.PictureMobile` получает и мобильную картинку и ставит перед основными источниками
  `<source media type="image/webp">` и `<source media type="image/jpeg">` со своими `srcset`, `width`, `height`
  (без скачка вёрстки). Браузер скачивает одну из двух. Картинка для соцсетей (`og:image`) — всегда основная.
- Админка — режим «Компьютер / Телефон» (админка рассчитана на JavaScript): кнопки ширины в живом предпросмотре
  переключают и ширину, и режим полей картинок. В режиме телефона
  выбор картинки показывает мобильную; пусто — превью основной, приглушённое, с подписью «как на компьютере».
  Поле мобильной картинки всегда в форме (в режиме компьютера скрыто), поэтому сохранение не зависит от режима.
  На узком экране (вкладки) — тот же переключатель над формой.
- Пометка: у блока, элемента галереи и обложки, где задана мобильная картинка, — метка «Своя для телефона»
  в обоих режимах; видно, не переключаясь.
- Данные: в JSON блока — `image_mobile` (у элемента галереи — тоже); миграции нет. Обложка — колонка `cover_mobile`
  в копиях поста (черновик и опубликованная) с внешним ключом на `images_files(id)`: миграция только добавляет
  колонку, данные не меняет. Мобильные картинки — в таблицах ссылок (`page_images`, `post_images`): используемую
  нельзя удалить из медиатеки. Мобильная без основной — ошибка у поля («Сначала выберите основную картинку»).
- Спецификация (подтверждено человеком): признак `mobile: true` у поля `image` — `spec v0.7.0`, только добавление,
  прежние `site.yaml` валидны. Валидатор: `mobile` — только у `image`. В эталоне — `cover: { type: image, mobile: true }`.
  У блоков признака нет: их поля описывает код сайта.

- [x] `spec v0.7.0`: `mobile` у `image` в `schema.json`, правило валидатора, пример в `spec/examples/invalid/`
      (`# expect: …`), `CHANGELOG.md`; релиз `make release MODULE=spec`, эталон — на новую версию
- [x] `web.MobileMedia`, `web.PictureMobile` (`web.Picture` — она же без мобильной); тест: с ней — два `<source media>` первыми и
      основная пара, без неё — разметка прежняя
- [x] Блоки `image`, `image_text`, элемент галереи: `image_mobile` — чтение, проверка, ссылки в `page_images`/`post_images`,
      вывод; e2e: сохранение, публикация копирует, используемую мобильную картинку нельзя удалить
- [x] Обложка поста: миграция `cover_mobile`, sqlc, форма, вывод на странице поста и в ленте; e2e как у блоков
- [x] Админка: режим «Компьютер / Телефон» (`static/live-preview.js` и выбор картинки), приглушённое превью
      наследуемой, метка «Своя для телефона»; браузерный тест: переключение режима, выбор мобильной, в предпросмотре
      «Телефон» показывает её (`currentSrc`), «Компьютер» — основную, сохранение в любом режиме
