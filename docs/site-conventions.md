# Конвенции сайтов

Часть корневого `AGENTS.md`: читается, когда задача касается этой темы.

## Конвенции сайтов

Эталонная реализация — `reference/`. Любой новый сайт повторяет её устройство.
Если конвенцию нужно изменить — сначала меняется `reference/` и этот раздел, потом скиллы.

Каждый сайт содержит:
- `site.yaml` — спецификация;
- `AGENTS.md` — короткое оглавление: версии модулей, команды, БД и миграции, карта «Документация» — какой файл
  `docs/` читать под задачу (обычными ссылками, не `@`-импортом: `AGENTS.md` загружается в каждую сессию, `docs/` — по необходимости);
- `docs/` — конвенции сайта по темам (`structure.md`, `content-types.md`, `admin.md`, `templates.md`, `media.md`,
  `seo.md`, `tests.md`, `deploy.md`);
- `CLAUDE.md` — одна строка `@AGENTS.md`;
- `Makefile` — единая точка входа (см. раздел «Makefile» в `AGENTS.md`);
- e2e-тесты ключевых сценариев (главная, раздел, публикация, загрузка изображения);
- запуск контрактных тестов из `testkit/` подключённых модулей.

Код сайта: стандартная библиотека Go, где её достаточно; `log/slog` для логов;
конфигурация через переменные окружения; один бинарник.

**Стек сайта**
- SQLite через `modernc.org/sqlite` (без CGO).
- Доступ к данным — sqlc; миграции — goose (только библиотека: их применяет подкоманда `site migrate`, CLI goose не нужен).
- Файлы `queries.sql` — только ASCII, включая комментарии: sqlc для SQLite режет текст запросов по байтовым смещениям,
  и кириллица обрезает запросы. Русские тексты — через параметры. В миграциях кириллица допустима.
- Бинарник: `site serve | migrate | seed`. `serve` не стартует при непримененных миграциях;
  `/healthz` отдаёт версию сборки и состояние схем (`version`, `pending` для каждого модуля и сайта).
- Шаблоны — templ; интерактивность — htmx; стили — чистый CSS, без Node в сборке. Страницы рендерит сервер, SPA нет.
- Публичный сайт работает без JavaScript: содержание, навигация и формы — HTML и CSS; скрипты — только улучшения
  поверх (поисковики, скорость, посетители с отключённым или упавшим скриптом).
- Админка рассчитана на JavaScript: htmx и свой JS (`static/`, небольшие файлы без зависимостей и сборки — панель
  Markdown, живой предпросмотр) — её часть, а не надстройка. Запасной вариант без скрипта не делается; уже
  работающий без скрипта код (обычный POST форм) не ломаем без причины. Сбой загрузки скрипта — ошибка, которую
  исправляют, а не сценарий, под который проектируют.
- Статика (CSS, `htmx.min.js`) вендорится и встраивается через `embed`.
- Сторонние скрипты, стили и шрифты сайта — только вендоренными файлами в `static/` (через `embed`, ссылка — `static.Path`),
  с версией в имени файла (`htmx-2.0.11.min.js`, `inter-4.1-cyrillic-400.woff2`); с CDN и Google Fonts не подключаются.
  Почему: сайт не зависит от чужого сервера и не передаёт ему IP посетителей; файл не меняется без коммита;
  `static.Path` кэширует его на год. Источник и контрольную сумму файла (sha512 из npm или релиза) сверить при вендоринге.
  Шрифты — `woff2` и `@font-face` в CSS сайта с `font-display: swap`, только нужные начертания и наборы символов;
  лицензия шрифта (обычно OFL) — файлом рядом. Внешние сервисы (счётчики аналитики, карты, видео) — не файлы, а
  встраивания; правило на них не распространяется, подключение решается отдельно для каждого сайта.
- `richtext` — Markdown: модуль `modules/richtext` (goldmark + санитайзер HTML, типографика); в админке textarea с превью через htmx.
  Сайт подключает контрактный тест модуля (`testkit.Run`) на настоящем выводе страницы.
- Сгенерированный код (sqlc, templ) коммитится; CI проверяет, что генерация ничего не меняет.
- Линтер — golangci-lint с общим минимальным конфигом, версия закреплена в `Makefile`.
- Версия Go в `go.mod`: актуальный релиз минус один минор (сейчас `go 1.26.0`). Тулчейн разработки закреплён директивой
  `toolchain` (сейчас `go1.27.2`) в `go.work` и каждом `go.mod`; при `GOTOOLCHAIN=auto` Go скачивает его сам.
  Инструменты, запускаемые через `go run tool@vX.Y.Z`, вызываются с `GOTOOLCHAIN=$(GO_TOOLCHAIN)` из `Makefile`,
  иначе они соберутся старым тулчейном и не разберут код новой версии языка.

**Структура сайта**
```
cmd/site/                  # main.go (конфиг, подкоманды, порядок источников миграций), server.go, seed.go
internal/database/         # открытие SQLite, статус схем, снимок, применение миграций
internal/content/<type>/   # модель, sqlc-запросы, хендлеры, templ одного типа контента (миграции — в db/migrations/)
internal/admin/            # страница входа и оболочка админки (меню, дашборд) поверх модуля auth; редактор записи с живым предпросмотром
internal/media/            # медиатека в админке поверх модуля images
internal/filelib/          # раздел «Файлы» в админке поверх модуля files
internal/blocks/           # поля blocks: типы блоков (структура, проверка, вывод, форма), JSON
internal/listfield/        # поля list: id и порядок элементов, кнопки «↑ ↓ Убрать / Добавить», JSON
internal/web/              # layout, общие компоненты templ
internal/seo/              # sitemap.xml, rss.xml, robots.txt (адреса и записи отдают типы контента)
internal/seofields/        # SEO записи вручную (заголовок, описание, картинка): поля, форма с превью сниппета
internal/menu/             # меню (main, footer): пункты на страницу по id, свой адрес или раздел с подпунктами из записей; раздел в админке
internal/settings/         # настройки сайта (одна запись: контакты, картинка для соцсетей, баннер cookies, коды вебмастеров) и их раздел в админке
internal/slug/             # slug из заголовка (транслитерация кириллицы) и проверка формата
db/migrations/             # миграции сайта (goose, своя таблица версий) + embed.go
deploy/                    # юниты systemd (serve, migrate, backup + таймер), пример site.env; Dockerfile — в корне сайта
static/                    # CSS, htmx-<версия>.min.js, свой JS админки (editor.js, live-preview.js) — через embed
docs/                      # конвенции сайта по темам; AGENTS.md — оглавление с картой этих файлов
site.yaml, sqlc.yaml, Makefile, AGENTS.md, CLAUDE.md
```
Группировка по типу контента, а не по слою: `add-section` добавляет одну папку.

**Тесты**
- e2e на чистом Go: `httptest` + goquery; htmx-запросы — обычные HTTP с заголовком `HX-Request`.
- Браузерные тесты админки (htmx и свой JS) — chromedp, целью `make e2e-browser` (тег сборки `browser`, чтобы
  `make test` не требовал Chrome); раз админка рассчитана на JavaScript, у каждого его поведения есть браузерный тест,
  и `make check` их запускает.

**Эксплуатация**
- Основной вариант — бинарник под systemd на VPS: `make build` (статический, версия вшита), юниты в `deploy/`
  (`site.service`; `site-migrate.service` — миграции только вручную; `site-backup.service` с таймером); Dockerfile — опция (`make docker`).
- `site backup` / `make backup` (ночью — таймер systemd): снимок БД и архив загрузок с локального диска (`DATA_DIR/uploads` и `DATA_DIR/files`). При хранилище S3 загрузки защищает версионирование бакета.
- litestream — опция, описывается в `docs/deploy.md` сайта, но не обязательна.
