# AGENTS.md

Инструкции для ИИ-агентов (Claude Code и др.), работающих в этом репозитории.
Проект называется **Keelkit**. Имя в коде, CLI и путях — `keelkit` (строчными).
Путь модулей — `github.com/voffkin/keelkit/modules/<name>`; модуль спецификации — `github.com/voffkin/keelkit/spec`. Репозиторий приватный (`https://github.com/voffkin/keelkit`), модули подключаются через `GOPRIVATE` (см. «Доступ к модулям»); лицензия MIT.

Метафора: закладка киля — первый шаг постройки корабля. Модули — киль, общая основа;
сайт — корабль, который строится на ней и дальше плывёт самостоятельно.

## Что это за проект

Набор переиспользуемых Go-модулей, спецификаций и скиллов для быстрого создания сайтов:
блогов, новостных сайтов, каталогов, сайтов-визиток.

Каждый созданный сайт — **самостоятельное Go-приложение в отдельном репозитории**.
Его можно развивать вручную или с агентом. Общие модули он подключает как обычные версионируемые зависимости.

Ключевое требование — **обновляемость старых сайтов**. Сайт, созданный годы назад,
должен получать исправления и новые возможности общих модулей через обновление
зависимости, проверку и пересборку.

## Главные принципы

1. **Писать код дёшево, проверять дорого.** Вкладываемся в спецификации, тесты и конвенции, а не в шаблонизаторы.
2. **В модули выносим только сложное, рискованное и одинаковое везде.** Всё, что отличается от сайта к сайту, генерируется агентом в код сайта.
3. **Спецификация — источник правды о структуре сайта.** Код — производная, которую можно дорабатывать.
4. **Однородность парка сайтов обеспечивают конвенции и тесты**, а не шаблоны. Агент обязан следовать эталонному сайту.
5. **Живые данные неприкосновенны.** Миграции БД — зона строгих правил (см. ниже).
6. **Никакого преждевременного обобщения.** Абстракция появляется, когда её подтвердили минимум два сайта.
   Исключение — код, связанный с безопасностью и одинаковый на любом сайте (вход, сессии, санитайзер HTML): он выносится
   в модуль сразу, чтобы исправления доезжали до сайтов через `go get`, а не правкой кода каждого сайта.

## Что куда

| Где | Что | Почему |
|---|---|---|
| Версионируемые модули (`modules/`) | изображения (`images`), файлы (`files`, с этапа 10.5) и хранилища; `richtext` и `auth` (с этапа 10.4); позже — SEO/sitemap/RSS, поиск | сложно, связано с безопасностью, должно обновляться через `go get` |
| Модуль спецификации (`spec/`) | JSON Schema `site.yaml` и валидатор `spec-validate` | общий для всех сайтов и скиллов; вызывается через `go run …@vX`, в код сайта не копируется |
| Код сайта (генерирует агент) | типы контента: страницы, статьи, новости, товары, категории; маршруты; админка; шаблоны | отличается от сайта к сайту, легко пишется по спецификации |
| Эталонный сайт (`reference/`) | образец того, как устроен и пишется любой сайт | по нему агент воспроизводит конвенции |

Если сомневаешься, куда положить новую функциональность, — по умолчанию в код сайта.
Вынос в модуль обсуждается с человеком.

SEO, sitemap и RSS на первом этапе пишутся в коде эталона и выносятся в модули после второго сайта.
Авторизация (одна таблица пользователей; «простой режим» — один пользователь, роли добавятся позже) и `richtext`
вынесены в модули `auth` и `richtext` до первого реального сайта (принцип 6, исключение; этап 10.4 в `PLAN.md`).
Страница входа и оболочка админки остаются в коде сайта: модуль не знает о вёрстке.

**`go.work` и честность зависимостей.** `go.work` коммитится и связывает модули и `reference/` для локальной разработки.
`reference/` при этом — полноценный модуль с конкретными версиями модулей в `go.mod`, без `replace`,
и собирается и тестируется с `GOWORK=off` (`make test-isolated`), как настоящий сайт. Поэтому изменение API модуля — два шага:
релиз модуля с тегом, затем обновление версии в `reference/`.

Второй и последующие сайты живут в отдельных репозиториях, не в монорепо.

## Правила для модулей

**Версионирование**
- Каждый модуль в `modules/<name>` имеет свой `go.mod` и версионируется независимо.
- Теги: `modules/<name>/vX.Y.Z` (формат, который понимает Go для вложенных модулей).
- Модуль `spec/` подчиняется тем же правилам (свой `go.mod`, `CHANGELOG.md`, `v0.x`, `GOWORK=off`); теги — `spec/vX.Y.Z`.
- Строгий semver. Ломающее изменение — новая мажорная версия с суффиксом пути `/vN`.
- До завершения первого этапа (второй сайт) модули живут в `v0.x`; затем `v1.0.0` и строгий semver.
- Теги ставятся только через `make release MODULE=<name> VERSION=vX.Y.Z`: цель проверяет запись в `CHANGELOG.md`, `UPGRADE.md` для изменений, требующих действий, и проходит `make check MODULE=<name>` (см. «CI»).
  «Требует действий» — в разделе версии в `CHANGELOG.md` есть `### Changed`, `### Removed`, `### Deprecated` или ссылка на `UPGRADE.md`;
  тогда в `UPGRADE.md` обязателен раздел `## vX.Y.Z`. Ещё проверяются: чистое дерево, ветка `main`, совпадение с `origin/main`,
  путь модуля для мажорной версии (`/vN` с v2), отсутствие `replace`. Тег сразу отправляется в `origin`.
- Модуль обязан собираться и проходить тесты с `GOWORK=off`, то есть только на опубликованных версиях зависимостей. Нельзя выпускать модуль, который работает лишь с неопубликованным кодом соседа.
- Опубликованный тег неизменяем: его не удаляют и не переставляют. У приватного модуля это не проверяет `sum.golang.org`,
  поэтому `make release` отказывается ставить уже существующий тег. Ошибка в релизе исправляется новой версией.

**Доступ к модулям**
- Репозиторий приватный. Go берёт модули прямо из git, минуя публичный прокси и базу контрольных сумм (`GOPRIVATE`),
  а для `github.com` всегда обращается по HTTPS — правило git `insteadOf` переводит эти адреса на SSH.
- Обе настройки экспортируются в `Makefile` (корня монорепо и каждого сайта) и действуют только на процессы `make`:
  `GOPRIVATE=github.com/voffkin/*` и `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_0`/`GIT_CONFIG_VALUE_0`
  (`url.git@github.com:voffkin/.insteadOf https://github.com/voffkin/`, git ≥ 2.31). Глобальные настройки git и Go не меняются;
  локальный `.git/config` не подходит — Go клонирует модули в свой кэш и запускает git там.
- От машины разработки нужен только SSH-ключ с доступом к репозиторию (проверка: `ssh -T git@github.com`).
  Чтобы и gopls в IDE (он запускается вне `make`) не ходил за модулями в публичный прокси, можно один раз выполнить
  `go env -w 'GOPRIVATE=github.com/voffkin/*'` (кавычки обязательны: zsh раскрывает `*`).
- В CI — SSH-ключ только для чтения (deploy key) в секрете `KEELKIT_DEPLOY_KEY`; джоба поднимает с ним `ssh-agent`.
  Пока CI запускается вручную, ключ не обязателен (см. «CI»).
- «Опубликованная версия» = тег, запушенный в этот репозиторий. Порядок релиза: тег модуля → push → обновление версии в `reference/go.mod`.

**API**
- Публичный API минимален. Всё, что можно, — в `internal/`.
- Никакого общего «core»-модуля с общими типами. Модули связываются через маленькие интерфейсы, объявленные на стороне потребителя.
- Модуль не знает о шаблонах и вёрстке сайта. Он отдаёт данные, сервисы и, при необходимости, `http.Handler`.
- Зависимости от внешних библиотек — только оправданные (см. раздел «Зависимости»).

**Миграции**
- Модуль владеет своими таблицами и хранит миграции в `migrations/` через `embed.FS`.
- Инструмент — goose; у каждого модуля своя таблица версий (`goose_<module>_version`), у сайта — своя.
- Версия схемы учитывается отдельно для каждого модуля.
- Только прямые миграции (down-секции не пишем — это конвенция, goose их не запрещает). Удаление и переименование колонок — в два этапа (добавить новое → перенести данные → удалить старое в следующей версии).
- Миграция, меняющая существующие данные, требует теста на копии реалистичных данных и явного упоминания в `UPGRADE.md`.
- Миграции применяются только явной командой `site migrate` (`make migrate`), никогда при старте.
  Порядок: модули в порядке из `site.yaml`, затем миграции сайта. Бинарник отказывается стартовать при непримененных миграциях.
- Перед применением миграций `site migrate` обязательно делает снимок БД (`VACUUM INTO`) и без него не продолжает.

**Тесты и документация к релизу**
- `testkit/` — контрактные тесты, которые сайт запускает у себя, чтобы убедиться, что интеграция не сломалась.
- `CHANGELOG.md` — для людей.
- `UPGRADE.md` — для агентов: для каждой версии, требующей действий, описать, что изменилось, какие изменения нужны в коде сайта, как проверить результат, нужна ли повторная обработка данных.

## Модуль изображений (первый)

- Загрузка, валидация, обработка (размеры, форматы), хранение.
- Хранилище за интерфейсом `Storage`: пока локальный диск; S3-совместимое отложено до появления потребности.
- У каждого файла хранится **версия профиля обработки**.
- Повторная обработка — штатная идемпотентная команда модуля («переобработать всё с версией профиля ниже N»), безопасная для прерывания и повторного запуска.
- Новые форматы и правила применяются к новым загрузкам автоматически, к старым — только через повторную обработку.
- `Service` (`NewService(db, storage, Config)`): `Upload`, `Get`, `List`, `Delete`, `Reprocess`, `Handler`.
  Метаданные — в таблицах `images_*` базы сайта (SQLite), запросы — `database/sql` без sqlc; сайт к этим таблицам
  обращается только через `Service`, а ссылается на изображение внешним ключом на `images_files(id)`.
- id изображения — 128 случайных бит (base32, 26 символов): адреса не перебираются по порядку.
- Раскладка в хранилище: оригинал `<id>/original.<ext>`, варианты `<id>/v<профиль>/<ширина>.<webp|jpg>`.
  Версия профиля в пути меняет адрес при повторной обработке, поэтому `Handler` отдаёт варианты с
  `Cache-Control: public, max-age=31536000, immutable`. Оригинал (EXIF с GPS) `Handler` не отдаёт никогда.
- Одновременных обработок не больше `Config.MaxConcurrent` (по умолчанию 2: фото 40 Мп — ~400 МБ памяти); остальные ждут.
- `Reprocess(ctx, below)` поднимает изображения с версией ниже `below` до `ProfileVersion`; `below` выше текущей
  версии равносилен ей, поэтому повторный запуск ничего не делает. Файлы, на которые больше нет ссылок, сначала
  записываются в `images_trash` в той же транзакции, что и изменение строк, и удаляются после неё — прерывание в
  любой момент не теряет и не оставляет файлов (остатки убирает следующий `Delete` или `Reprocess`).
- Тесты модуля используют `modernc.org/sqlite` и goose (те же версии, что у сайтов); в код сайта они не попадают.
- Без CGO: ресайз — `golang.org/x/image/draw`, декодирование WebP — `golang.org/x/image/webp`,
  кодирование WebP — `gen2brain/webp` (libwebp, транслированная из WASM в чистый Go).

**Профиль обработки v1**
- Оригинал хранится всегда и побайтно, с EXIF и GPS (без него повторная обработка невозможна) — поэтому публично не отдаётся.
- Ширины 480 / 960 / 1600 / 2400 px, без увеличения; оригинал меньше 2400 px получает ещё вариант своей ширины.
- Выход: WebP q=80 и JPEG q=82 как фолбэк. AVIF — позже, новой версией профиля.
- EXIF удаляется; ориентация применяется до удаления.
- Лимиты: 20 МБ на файл, 40 мегапикселей (защита от decompression bomb).
- Вход: JPEG, PNG, WebP (без анимации). HEIC не поддерживается (нет декодера без CGO).
- Прозрачность: WebP сохраняет альфа-канал, JPEG — на белом фоне. ICC-профили не переносятся (варианты считаются sRGB).

## Модуль файлов (`modules/files`)

- Файлы, которые хранятся как есть, без вариантов: PDF, видео MP4 и WebM, SVG. Формат — по содержимому (сигнатура,
  у MP4 — бренд `ftyp`, у SVG — корневой элемент XML), а не по имени и не по `Content-Type` загрузки.
- Лимит — `Config.MaxBytes`, по умолчанию 50 МБ (сканы PDF бывают под 20 МБ); сайт с видео поднимает его.
  Загрузка идёт потоком в хранилище, превышение обрывает запись (`ErrTooLarge`), ничего не остаётся.
- Адрес — `<id>/<имя>.<ext>` (`File.Path`): имя составляется из исходного при загрузке и не меняется;
  `Replace` (только тем же форматом — `ErrFormatMismatch`) пишет новый ключ хранилища и переключает строку
  в транзакции, старый файл — через `files_trash`, как у `images`. Поэтому кэш — `public, no-cache` с `ETag` версии,
  а не `immutable`. Другое имя при верном id — 404: у файла один адрес.
- `Handler` — `http.ServeContent`: Range и If-Range (видео перематывается), If-None-Match; всегда `nosniff`.
  SVG не очищается, а отдаётся с `Content-Security-Policy: sandbox; default-src 'none'; …`: скрипты в файле не
  выполняются и по прямому адресу; в `<img>` браузер их не выполняет и так. PDF — без CSP: `sandbox` ломает
  встроенный просмотрщик PDF.
- Ссылка из контента — внешним ключом на `files_files(id)` без `ON DELETE`: используемый файл не удаляется.
- Тесты модуля — `modernc.org/sqlite` и goose, как у `images`; `testkit.Run` — контракт для сайтов.

## Спецификация сайта

- Формат: YAML, валидируется по `spec/schema.json` командой `make spec-validate FILE=...`
  (модуль `spec`, CLI `spec/cmd/spec-validate`). Ошибки выводятся как `файл:строка:столбец: /json/pointer: сообщение`.
- Правила, не выражаемые в JSON Schema, проверяет валидатор: `ref` указывает на существующий тип контента,
  `to` — только у `ref`, `mobile` — только у `image`, `allow` — только у `blocks`, `fields` — только у `list`, в типе не больше одного поля `slug`,
  служебные имена полей запрещены (у типа — `id`, `created_at`, `updated_at`, `draft`, `publish_date`, `seo_title`,
  `seo_description`, `seo_image`, `sort_order`; в `settings` — `id`, `updated_at`; у элемента `list` — `id`), feature `seo` — только
  у типа с полем `slug`, в `settings` нет полей `slug` и `blocks`.
- Новое правило схемы — пример в `spec/examples/invalid/` с ожидаемым текстом ошибки (`# expect: …`).
- Хранится в репозитории сайта как `site.yaml`.
- Описывает: разделы и типы контента (поля, связи, правила), подключённые модули и их версии, настройки (языки, SEO, хранилище).
  В `modules` — все модули Keelkit из `go.mod` сайта, в том числе без таблиц (`richtext`), в порядке применения миграций;
  сайт сверяет этот список с `go.mod` и источниками миграций тестом (в эталоне — `TestSpecModulesMatchCode`).
- Структурные изменения сайта вносятся сначала в спецификацию, затем в код.
- Схему спецификации меняем осознанно: у неё есть версия, для старых версий нужен путь миграции.

**Версия схемы 1**
- Типы полей: `string`, `text`, `richtext` (Markdown), `int`, `bool`, `date`, `image`, `ref`, `slug`, `blocks`
  (с `spec v0.2.0`; `allow: [имена блоков]` — обязателен, непустой, без повторов; поля блоков описывает код сайта),
  `list` (с `spec v0.3.0`; `fields: {…}` — поля элемента: типы `string`…`ref`, без `slug`, `blocks` и вложенных `list`).
- Features: `draft`, `publish_date`, `rss`, `sitemap`, `seo` (с `spec v0.3.0`: SEO записи вручную — поля `seo_*`
  добавляет feature, в `fields` их не пишут; только у типа со своим адресом, то есть с полем `slug`), `order`
  (с `spec v0.5.0`: ручной порядок записей — кнопки ↑ ↓ в списке админки, тот же порядок на сайте; колонка `sort_order`).
- `settings: { fields: {…} }` (с `spec v0.3.0`) — одна запись настроек сайта, поля как у типа контента, кроме `slug` и `blocks`.
- `mobile: true` у поля `image` (с `spec v0.7.0`): своя картинка для узкого экрана; не задана — та же, что на
  компьютере. У полей блоков признака нет — их описывает код сайта.
- `modules`: `images`, `richtext`, `auth` (последние два — с `spec v0.4.0`), `files` (с `spec v0.6.0`), значение — мажорная версия (`v0`).
- `menus: [main, footer]` (с `spec v0.3.0`) — меню, которые редактируют в админке; устройство пунктов — код сайта.
- Ровно один язык: поле `languages` есть, но допускает один элемент. Мультиязычность — `spec_version: 2`.

Пример (ориентир, не окончательная схема):

```yaml
spec_version: 1
site:
  name: my-blog
  languages: [ru]
modules:
  images: v0
content:
  pages:
    fields:
      title: { type: string, required: true }
      body:  { type: richtext }
  posts:
    fields:
      title:    { type: string, required: true }
      body:     { type: richtext }
      cover:    { type: image }
      category: { type: ref, to: categories }
    features: [publish_date, draft, rss, sitemap]
  categories:
    fields:
      name: { type: string, required: true }
```

## Скиллы

Скиллы — тоже софт: версионируются, имеют эвалы в `skills/evals/`, обновляются вместе с модулями.

Распространяются как плагин Claude Code: монорепо — маркетплейс плагинов. Сайт указывает в своём `AGENTS.md`
минимальную версию плагина. Скиллы не копируются в репозитории сайтов: скилл обновления должен быть свежее сайта.

Эвалы требуют вызовов LLM, поэтому в CI запускаются вручную (`workflow_dispatch`) и обязательно перед релизом скилла.

Планируемые скиллы:
- **create-site** — задаёт вопросы, составляет `site.yaml`, создаёт репозиторий сайта по образцу `reference/`.
- **add-section** — добавляет тип контента: правка спецификации → миграция в `db/migrations/` → код в `internal/content/<type>/` → тесты.
- **upgrade-site** — поднимает версии модулей, применяет `UPGRADE.md`, прогоняет тесты, готовит PR.
- **reprocess-images** — решает, нужна ли повторная обработка, и запускает её.
- **check-drift** (позже) — ищет расхождения между спецификацией и кодом.

Эвал скилла: по заданной спецификации результат собирается, проходит тесты и соответствует конвенциям эталонного сайта.

## Конвенции сайтов

Эталонная реализация — `reference/`. Любой новый сайт повторяет её устройство.
Если конвенцию нужно изменить — сначала меняется `reference/` и этот раздел, потом скиллы.

Каждый сайт содержит:
- `site.yaml` — спецификация;
- `AGENTS.md` — конвенции сайта, ссылка на используемые версии модулей и что нужно для доступа к ним (SSH-ключ, см. «Доступ к модулям»);
- `CLAUDE.md` — одна строка `@AGENTS.md`;
- `Makefile` — единая точка входа (см. раздел «Makefile»);
- e2e-тесты ключевых сценариев (главная, раздел, публикация, загрузка изображения);
- запуск контрактных тестов из `testkit/` подключённых модулей.

Код сайта: стандартная библиотека Go, где её достаточно; `log/slog` для логов;
конфигурация через переменные окружения; один бинарник.

**Стек сайта**
- SQLite через `modernc.org/sqlite` (без CGO).
- Доступ к данным — sqlc; миграции — goose (только библиотека: их применяет подкоманда `site migrate`, CLI goose не нужен).
- Файлы `queries.sql` — только ASCII, включая комментарии: sqlc для SQLite режет текст запросов по байтовым смещениям,
  и кириллица обрезает запросы. Русские тексты — через параметры. В миграциях кириллица допустима.
- Бинарник: `site serve | migrate | seed`. `serve` не стартует при непримененных миграциях;
  `/healthz` отдаёт версию сборки и состояние схем (`version`, `pending` для каждого модуля и сайта).
- Шаблоны — templ; интерактивность — htmx; стили — чистый CSS, без Node в сборке. Страницы рендерит сервер, SPA нет.
- Публичный сайт работает без JavaScript: содержание, навигация и формы — HTML и CSS; скрипты — только улучшения
  поверх (поисковики, скорость, посетители с отключённым или упавшим скриптом).
- Админка рассчитана на JavaScript: htmx и свой JS (`static/`, небольшие файлы без зависимостей и сборки — панель
  Markdown, живой предпросмотр) — её часть, а не надстройка. Запасной вариант без скрипта не делается; уже
  работающий без скрипта код (обычный POST форм) не ломаем без причины. Сбой загрузки скрипта — ошибка, которую
  исправляют, а не сценарий, под который проектируют.
- Статика (CSS, `htmx.min.js`) вендорится и встраивается через `embed`.
- Сторонние скрипты, стили и шрифты сайта — только вендоренными файлами в `static/` (через `embed`, ссылка — `static.Path`),
  с версией в имени файла (`htmx-2.0.11.min.js`, `inter-4.1-cyrillic-400.woff2`); с CDN и Google Fonts не подключаются.
  Почему: сайт не зависит от чужого сервера и не передаёт ему IP посетителей; файл не меняется без коммита;
  `static.Path` кэширует его на год. Источник и контрольную сумму файла (sha512 из npm или релиза) сверить при вендоринге.
  Шрифты — `woff2` и `@font-face` в CSS сайта с `font-display: swap`, только нужные начертания и наборы символов;
  лицензия шрифта (обычно OFL) — файлом рядом. Внешние сервисы (счётчики аналитики, карты, видео) — не файлы, а
  встраивания; правило на них не распространяется, подключение решается отдельно для каждого сайта.
- `richtext` — Markdown: модуль `modules/richtext` (goldmark + санитайзер HTML, типографика); в админке textarea с превью через htmx.
  Сайт подключает контрактный тест модуля (`testkit.Run`) на настоящем выводе страницы.
- Сгенерированный код (sqlc, templ) коммитится; CI проверяет, что генерация ничего не меняет.
- Линтер — golangci-lint с общим минимальным конфигом, версия закреплена в `Makefile`.
- Версия Go в `go.mod`: актуальный релиз минус один минор (сейчас `go 1.26.0`). Тулчейн разработки закреплён директивой
  `toolchain` (сейчас `go1.27.2`) в `go.work` и каждом `go.mod`; при `GOTOOLCHAIN=auto` Go скачивает его сам.
  Инструменты, запускаемые через `go run tool@vX.Y.Z`, вызываются с `GOTOOLCHAIN=$(GO_TOOLCHAIN)` из `Makefile`,
  иначе они соберутся старым тулчейном и не разберут код новой версии языка.

**Структура сайта**
```
cmd/site/                  # main.go (конфиг, подкоманды, порядок источников миграций), server.go, seed.go
internal/database/         # открытие SQLite, статус схем, снимок, применение миграций
internal/content/<type>/   # модель, sqlc-запросы, хендлеры, templ одного типа контента (миграции — в db/migrations/)
internal/admin/            # страница входа и оболочка админки (меню, дашборд) поверх модуля auth; редактор записи с живым предпросмотром
internal/media/            # медиатека в админке поверх модуля images
internal/filelib/          # раздел «Файлы» в админке поверх модуля files
internal/blocks/           # поля blocks: типы блоков (структура, проверка, вывод, форма), JSON
internal/listfield/        # поля list: id и порядок элементов, кнопки «↑ ↓ Убрать / Добавить», JSON
internal/web/              # layout, общие компоненты templ
internal/seo/              # sitemap.xml, rss.xml, robots.txt (адреса и записи отдают типы контента)
internal/seofields/        # SEO записи вручную (заголовок, описание, картинка): поля, форма с превью сниппета
internal/menu/             # меню (main, footer): пункты на страницу по id, свой адрес или раздел с подпунктами из записей; раздел в админке
internal/settings/         # настройки сайта (одна запись: контакты, картинка для соцсетей, баннер cookies, коды вебмастеров) и их раздел в админке
internal/slug/             # slug из заголовка (транслитерация кириллицы) и проверка формата
db/migrations/             # миграции сайта (goose, своя таблица версий) + embed.go
static/                    # CSS, htmx-<версия>.min.js, свой JS админки (editor.js, live-preview.js) — через embed
site.yaml, sqlc.yaml, Makefile, AGENTS.md, CLAUDE.md
```
Группировка по типу контента, а не по слою: `add-section` добавляет одну папку.

**Тесты**
- e2e на чистом Go: `httptest` + goquery; htmx-запросы — обычные HTTP с заголовком `HX-Request`.
- Браузерные тесты админки (htmx и свой JS) — chromedp, целью `make e2e-browser` (тег сборки `browser`, чтобы
  `make test` не требовал Chrome); раз админка рассчитана на JavaScript, у каждого его поведения есть браузерный тест,
  и `make check` их запускает.

**Эксплуатация**
- Основной вариант — бинарник под systemd на VPS; Dockerfile — опция.
- `make backup` (по cron): снимок БД и архив загрузок с локального диска (`DATA_DIR/uploads` и `DATA_DIR/files`). При хранилище S3 загрузки защищает версионирование бакета.
- litestream — опция, описывается в `AGENTS.md` сайта, но не обязательна.

## Makefile — единая точка входа

И в монорепо, и в каждом сайте все команды запускаются через `make`. Это касается людей, агентов и CI.

- Любая регулярная операция — отдельная цель: сборка, запуск, тесты, линтеры, кодогенерация, миграции, повторная обработка изображений, релиз и т. д.
- CI и скиллы вызывают только цели `make`, а не `go ...` напрямую. Если нужной цели нет — сначала добавь её в `Makefile`.
- Цель по умолчанию — `help`: выводит список целей с описаниями.
- У каждой цели есть комментарий `## ...` с описанием и, если она принимает параметры, примером вызова.
- Параметры передаются переменными с безопасными значениями по умолчанию (`VAR ?= ...`).
- В корне монорепо `test`, `test-isolated`, `lint` без `MODULE` проходят по `modules/*`, `spec/` и `reference/`;
  `MODULE=<name>` — `modules/<name>`, `MODULE=spec` и `MODULE=reference` — одноимённые каталоги. `build`, `run`, `dev`, `migrate`, `backup`, `seed`, `user-create`, `reprocess-images`, `reset`, `generate`, `generate-check`, `e2e`, `e2e-browser` делегируются в `reference/Makefile`;
  `images-demo` — своя цель корня (демо-отчёт модуля `images`);
  `deps-check` — по тем же каталогам, что `test`; `check` — все проверки CI по тем же каталогам
  (`lint`, `test`, `test-isolated`, `deps-check`; для `reference/` ещё `generate-check`, `e2e` и `e2e-browser`, для `spec/` — `spec-validate` `reference/site.yaml`); `release` — `scripts/release.sh` (`DRY_RUN=1` — только проверки).
- Совместимость с GNU Make 3.81 (стоит по умолчанию на macOS): без `.ONESHELL`, `$(file ...)` и других возможностей 4.x.

Пример оформления:

```make
.DEFAULT_GOAL := help

# Модуль в modules/<MODULE>. Комментарий — на отдельной строке: иначе пробелы попадут в значение.
MODULE ?= images

help: ## Показать список целей
	@grep -hE '^[a-zA-Z0-9_-]+:.*## ' $(MAKEFILE_LIST) | awk 'BEGIN {FS = ":.*## "}; {printf "  %-20s %s\n", $$1, $$2}'

test: ## Тесты модуля. Пример: make test MODULE=images
	cd modules/$(MODULE) && go test ./...

test-isolated: ## Тесты модуля только на опубликованных зависимостях. Пример: make test-isolated MODULE=images
	cd modules/$(MODULE) && GOWORK=off go test ./...
```

## Зависимости

Правила действуют и для модулей, и для сайтов, и для инструментов (sqlc, templ, goose, golangci-lint, htmx).

**Перед добавлением или обновлением проверь**
- **Свежесть.** Берётся последняя стабильная версия, проверенная по реестру (`go list -m -versions <path>`, релизы на GitHub),
  а не по памяти: знания агента о версиях могут устареть. Не использовать pre-release (`-rc`, `-beta`),
  псевдоверсии (коммиты без тега) и `@latest` без фиксации конкретной версии — кроме случаев, согласованных с человеком.
- **Стабильность и поддержку.** У библиотеки есть теги semver, недавние релизы, живой репозиторий; она не помечена deprecated/archived.
  Лицензия совместима с MIT.
- **Совместимость.** Новая версия не конфликтует с остальными зависимостями:
  `go mod tidy` проходит без неожиданных изменений, в `go mod graph` нет двух мажорных версий одной библиотеки без причины,
  требуемая версия Go (`go` в её `go.mod`) не выше нашей политики версий Go.
- **Согласованность связанных пар.** Версии, которые должны совпадать, совпадают: CLI `templ` и библиотека `github.com/a-h/templ`,
  CLI `sqlc` и формат его конфига, `goose` CLI и библиотека.
- **Уязвимости.** `govulncheck` не находит известных уязвимостей в используемом коде.

**После изменения**
- Сборка, `make generate-check`, тесты и `make test-isolated` проходят.
- Версии инструментов закреплены в `Makefile` (`go run tool@vX.Y.Z` или директива `tool` в `go.mod`), а не берутся из окружения.
- Версия вендоренного файла (скрипт, шрифт) указана в имени файла (см. «Стек сайта»).
- Для модулей: обновление зависимости, влияющее на сайты, отражено в `CHANGELOG.md` (и в `UPGRADE.md`, если нужны действия).

Цель `make deps-check` выводит доступные обновления (`go list -m -u all`) и запускает `govulncheck`; она входит в CI.

## CI

**Сейчас (до этапа 14 в `PLAN.md`) CI на GitHub запускается только вручную (`workflow_dispatch`).** Решение человека:
проверки выполняются локально — `make check` (без `MODULE` — всё) перед коммитом в `main`, и обязательно перед тегом:
`make release` сам запускает `make check MODULE=<name>` и не ставит тег, если она не прошла. Так CI не нужен ни доступ
к приватным модулям (deploy key), ни `gh` с правами на репозиторий. Цена: нет проверки на чистой Linux-машине —
её вернёт этап 14 (автозапуск, path-фильтры, доступ к модулям). Для `reference/` `make check` запускает и
`e2e-browser` — нужен Chrome.

Целевое устройство (этап 14). GitHub Actions; джобы вызывают только цели `make`.
- Path-фильтры: изменения в `modules/<X>` или `spec/` запускают джобы для этого модуля и для `reference/`.
- Модуль: `make lint`, `make test`, `make test-isolated`, `make generate-check`, `make deps-check`.
- `reference/`: то же плюс `make e2e` и `make e2e-browser` (chromedp, Chrome есть на раннере), всё с `GOWORK=off`.
- Эвалы скиллов — вручную (`workflow_dispatch`).

## Как работать агенту

1. Перед изменениями прочитай этот файл и затронутую часть `reference/`.
2. Меняешь публичный API модуля — оцени, мажорное ли это изменение, и обнови `CHANGELOG.md` и `UPGRADE.md`.
3. Команды запускай через `make` (список — `make help`). После изменений: проверки и тесты затронутых модулей, в том числе с `GOWORK=off`, — через соответствующие цели.
4. Не выноси код в новый модуль и не добавляй внешние зависимости без согласования с человеком. Перед добавлением или обновлением любой зависимости выполни проверки из раздела «Зависимости».
5. Миграции, меняющие существующие данные, и изменения схемы спецификации — только после явного подтверждения человеком.
6. Если конвенция не описана — посмотри, как сделано в `reference/`, и предложи дописать правило сюда.
7. Правило противоречит задаче, требованиям или другому правилу, или его цена не оправдана — скажи об этом и предложи
   замену, а не обходи и не исполняй молча. Правила пишутся под задачи и меняются вместе с ними.

## Принятые решения

Решения ниже приняты человеком; не пересматривать без него.

| Вопрос | Решение | Почему |
|---|---|---|
| Путь модулей | `github.com/voffkin/keelkit`, без vanity-домена | путь совпадает с адресом репозитория; домена нет. Смена хоста — до релиза v0.1.0, позже путь окажется в импортах всех сайтов |
| Видимость | приватный репозиторий под аккаунтом `voffkin`; модули — через `GOPRIVATE` и доступ к git | публиковать код не обязательно; `GOPRIVATE` — штатный механизм Go для непубличных модулей, версии и `go get` работают как у публичных |
| Лицензия | MIT (файл `LICENSE` сохранён) | не мешает закрытому репозиторию и не требует действий, если код откроется |
| СУБД | SQLite (`modernc.org/sqlite`, без CGO) | один статический бинарник; хватает для целевых сайтов |
| Доступ к данным | sqlc | ошибки типов ловятся на генерации, а не в проде |
| Миграции | goose, таблица версий на модуль | свой мигратор привёл бы к дублированию или core-модулю |
| Шаблоны и фронт | templ + htmx + чистый CSS | ошибки шаблонов ловит компилятор; без Node |
| Изображения | x/image + `gen2brain/webp` (v0.6+: libwebp, транслированная в Go; раньше — WASM через wazero) | без CGO; профиль версионируется, можно сменить |
| Сборка с тегом `nodynamic` | сайты и монорепо собираются и тестируются с `-tags nodynamic` (`GOFLAGS` в `Makefile`): `gen2brain/webp` не подгружает системную libwebp | результат обработки одинаков на всех машинах и совпадает с тестами; бинарник не зависит от библиотек хоста. Цена — системная libwebp была бы быстрее |
| Картинки в контенте | только блоками (этап 8.5) с id изображения; синтаксиса картинок в Markdown нет, адреса вариантов в контенте не хранятся | адреса меняются при повторной обработке; внешний ключ на `images_files` защищает используемое изображение |
| Ориентация EXIF | свой минимальный парсер в `modules/images/internal/exif`: тег Orientation из JPEG (APP1), PNG (eXIf), WebP (EXIF) | ~150 строк без зависимостей; `rwcarlsen/goexif` без тегов semver, `dsoprea/go-exif` тяжёл ради одного тега |
| Авторизация | модуль `auth` (с этапа 10.4; до него — в коде эталона), одна таблица пользователей; страница входа и оболочка админки — код сайта | вход, сессии и CSRF одинаковы везде и связаны с безопасностью: исправления должны доезжать через `go get` (решение человека, 2026-10-13; раньше — «после второго сайта») |
| `richtext` | модуль `richtext` (с этапа 10.4; до него — `reference/internal/richtext`) | санитайзер — граница безопасности; исправления — через `go get` (решение человека, 2026-10-13) |
| Версии модулей | `v0.x` до второго сайта, затем `v1` | API подтверждается двумя сайтами |
| Скиллы | плагин Claude Code из монорепо | скилл обновления свежее обновляемого сайта |
| Валидатор спецификации | отдельный модуль `spec/` (`github.com/voffkin/keelkit/spec`): схема + `cmd/spec-validate` | сайты и `create-site` вызывают его через `go run …@vX`; зависимости валидатора не попадают в сайты |
| YAML и JSON Schema | `go.yaml.in/yaml/v3`, `santhosh-tekuri/jsonschema/v6` | `gopkg.in/yaml.v3` в архиве; преемник — `go.yaml.in/yaml/v3` |
| Санитайзер HTML для `richtext` | `microcosm-cc/bluemonday` (v1.0.27), политика UGC | стандарт де-факто, не в архиве, BSD-3; релизы редкие — goldmark и так вырезает сырой HTML, санитайзер — второй рубеж |
| Файлы (этап 10.5) | модуль `modules/files` (решение человека, 2026-10-13): PDF, MP4/WebM, SVG; лимит в `Config` (50 МБ); SVG без очистки, с CSP `sandbox` и `nosniff`; замена без смены адреса | хранилище и граница безопасности одинаковы на любом сайте (принцип 6); очистка SVG — сложный и хрупкий код, песочница браузера надёжнее |
| Хеширование паролей | argon2id из `golang.org/x/crypto/argon2` (v0.57.0); m=64 МиБ, t=3, p=4, соль 16 байт, ключ 32 байта; формат PHC `$argon2id$v=19$m=…,t=…,p=…$соль$хеш` | рекомендация OWASP и RFC 9106; нет лимита bcrypt в 72 байта; параметры хранятся в хеше — их можно усилить без миграции, перехешируя при входе |
| Ввод пароля в CLI | `golang.org/x/term` (v0.46.0), `term.ReadPassword` в `site user create` | без эха в терминале на всех ОС; модуль уже в графе через `golang.org/x/crypto`, зависит только от `x/sys` |
| Транслитерация для slug | своя таблица в `internal/slug` (кириллица → упрощённая латиница: ж→zh, х→kh, ц→ts, щ→shch, ю→yu, я→ya, ъ/ь опускаются) | ~40 строк без внешних зависимостей; другие алфавиты — по мере надобности |
| Где миграции типов контента | все миграции сайта — в `db/migrations/`; в `internal/content/<type>/` — запросы, хендлеры, templ | у goose одна последовательность версий на таблицу версий; sqlc читает схему из одного каталога |
| Страницы из блоков (этап 8.5) | тип поля `blocks` в спецификации: только имена блоков (`allow: [text, image, …]`), поля блоков — в коде `internal/blocks/`; посты — тоже блоки | набор блоков — дизайн сайта (принцип 2); один способ вставки картинок для страниц и постов |
| Хранение блоков | JSON-массив в колонке (`json_valid`) + таблица ссылок на картинки (`page_images` → `images_files(id)`), перезаписывается в той же транзакции | порядок сохраняется атомарно, черновик копируется одной колонкой; внешний ключ защищает используемые картинки |
| Модель черновика | отдельная копия: `<type>_contents(kind IN ('draft','published'))`; «Сохранить» пишет черновик, «Опубликовать» копирует его, «Снять с публикации» удаляет опубликованную копию; slug — часть версии | правки опубликованной страницы не видны до публикации; заменяет флажок `draft` |
| JavaScript в админке | админка рассчитана на JavaScript (htmx и свой JS без сборки), запасного варианта без скрипта нет; публичный сайт — без обязательного JavaScript (решение человека, 2026-10-14; раньше — «без JavaScript всё работает» и в админке) | админка — рабочий инструмент редактора в современном браузере; запасной вариант удваивал работу и толкал к неудобным решениям. Сайт смотрят посетители и поисковики — там правило остаётся |
| CI до этапа 14 | GitHub Actions только вручную (`workflow_dispatch`); проверки — локально `make check`, его вызывает `make release` вместо проверки зелёного CI | не нужны deploy key и `gh` с доступом к приватному репозиторию; полный CI — этап 14 |

## Открытые решения (не принимать без человека)

- **Доступ CI монорепо к опубликованным модулям** (отложено до этапа 14, пока CI запускается вручную — см. «CI»).
  Сейчас: deploy key только для чтения в секрете `KEELKIT_DEPLOY_KEY`. Альтернатива: встроенный `GITHUB_TOKEN` джобы
  (он читает этот же репозиторий) — без ключа и секрета; для этого `GIT_CONFIG_*` в `Makefile` должны переопределяться
  из окружения. Сайтам в отдельных репозиториях в любом случае нужен свой deploy key на `voffkin/keelkit`
  (один публичный ключ GitHub не даёт добавить в два репозитория).
