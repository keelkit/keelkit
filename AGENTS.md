# AGENTS.md

Инструкции для ИИ-агентов (Claude Code и др.), работающих в этом репозитории.
Проект называется **Keelkit**. Имя в коде, CLI и путях — `keelkit` (строчными).
Путь модулей — `github.com/keelkit/keelkit/modules/<name>`. Репозиторий публичный, лицензия MIT.

Метафора: закладка киля — первый шаг постройки корабля. Модули — киль, общая основа;
сайт — корабль, который строится на ней и дальше плывёт самостоятельно.

## Что это за проект

Набор переиспользуемых Go-модулей, спецификаций и скиллов для быстрого создания сайтов:
блогов, новостных сайтов, каталогов, сайтов-визиток.

Каждый созданный сайт — **самостоятельное Go-приложение в отдельном репозитории**.
Его можно развивать вручную или с агентом. Общие модули он подключает как обычные версионируемые зависимости.

Ключевое требование — **обновляемость старых сайтов**. Сайт, созданный годы назад,
должен получать исправления и новые возможности общих модулей через обновление
зависимости, проверку и пересборку.

## Главные принципы

1. **Писать код дёшево, проверять дорого.** Вкладываемся в спецификации, тесты и конвенции, а не в шаблонизаторы.
2. **В модули выносим только сложное, рискованное и одинаковое везде.** Всё, что отличается от сайта к сайту, генерируется агентом в код сайта.
3. **Спецификация — источник правды о структуре сайта.** Код — производная, которую можно дорабатывать.
4. **Однородность парка сайтов обеспечивают конвенции и тесты**, а не шаблоны. Агент обязан следовать эталонному сайту.
5. **Живые данные неприкосновенны.** Миграции БД — зона строгих правил (см. ниже).
6. **Никакого преждевременного обобщения.** Абстракция появляется, когда её подтвердили минимум два сайта.

## Что куда

| Где | Что | Почему |
|---|---|---|
| Версионируемые модули (`modules/`) | изображения, файлы и хранилища; позже — авторизация, SEO/sitemap/RSS, поиск | сложно, связано с безопасностью, должно обновляться через `go get` |
| Код сайта (генерирует агент) | типы контента: страницы, статьи, новости, товары, категории; маршруты; админка; шаблоны | отличается от сайта к сайту, легко пишется по спецификации |
| Эталонный сайт (`reference/`) | образец того, как устроен и пишется любой сайт | по нему агент воспроизводит конвенции |

Если сомневаешься, куда положить новую функциональность, — по умолчанию в код сайта.
Вынос в модуль обсуждается с человеком.

Авторизация (одна таблица пользователей; «простой режим» — один пользователь, роли добавятся позже),
SEO, sitemap и RSS на первом этапе пишутся в коде эталона и выносятся в модули после второго сайта.

## Структура репозитория

```
/
├── AGENTS.md
├── CLAUDE.md               # @AGENTS.md — для Claude Code
├── LICENSE                 # MIT
├── Makefile                # единая точка входа для всех команд
├── go.work                 # коммитится; в корне нет go.mod
├── .claude-plugin/         # монорепо — маркетплейс плагинов Claude Code со скиллами
├── .github/workflows/      # CI
├── modules/
│   └── images/             # первый модуль (свой go.mod)
│       ├── go.mod
│       ├── migrations/     # embed.FS, миграции только этого модуля
│       ├── testkit/        # контрактные тесты для сайтов
│       ├── CHANGELOG.md
│       └── UPGRADE.md      # инструкции по обновлению для агентов
├── spec/
│   ├── schema.json         # JSON Schema спецификации сайта
│   └── examples/           # примеры спецификаций
├── skills/                 # скиллы (create-site, add-section, upgrade-site, ...)
│   └── evals/              # эвалы скиллов
└── reference/              # эталонный сайт: страницы + блог (свой go.mod)
```

**`go.work` и честность зависимостей.** `go.work` коммитится и связывает модули и `reference/` для локальной разработки.
`reference/` при этом — полноценный модуль с конкретными версиями модулей в `go.mod`, без `replace`,
и в CI собирается и тестируется с `GOWORK=off`, как настоящий сайт. Поэтому изменение API модуля — два шага:
релиз модуля с тегом, затем обновление версии в `reference/`.

Второй и последующие сайты живут в отдельных репозиториях, не в монорепо.

## Правила для модулей

**Версионирование**
- Каждый модуль в `modules/<name>` имеет свой `go.mod` и версионируется независимо.
- Теги: `modules/<name>/vX.Y.Z` (формат, который понимает Go для вложенных модулей).
- Строгий semver. Ломающее изменение — новая мажорная версия с суффиксом пути `/vN`.
- До завершения первого этапа (второй сайт) модули живут в `v0.x`; затем `v1.0.0` и строгий semver.
- Теги ставятся только через `make release MODULE=<name> VERSION=vX.Y.Z`: цель проверяет запись в `CHANGELOG.md`, `UPGRADE.md` для изменений, требующих действий, и зелёный CI.
- Модуль обязан собираться и проходить тесты с `GOWORK=off`, то есть только на опубликованных версиях зависимостей. Нельзя выпускать модуль, который работает лишь с неопубликованным кодом соседа.

**API**
- Публичный API минимален. Всё, что можно, — в `internal/`.
- Никакого общего «core»-модуля с общими типами. Модули связываются через маленькие интерфейсы, объявленные на стороне потребителя.
- Модуль не знает о шаблонах и вёрстке сайта. Он отдаёт данные, сервисы и, при необходимости, `http.Handler`.
- Зависимости от внешних библиотек — только оправданные (см. раздел «Зависимости»).

**Миграции**
- Модуль владеет своими таблицами и хранит миграции в `migrations/` через `embed.FS`.
- Инструмент — goose; у каждого модуля своя таблица версий (`goose_<module>_version`), у сайта — своя.
- Версия схемы учитывается отдельно для каждого модуля.
- Только прямые миграции (down-секции не пишем — это конвенция, goose их не запрещает). Удаление и переименование колонок — в два этапа (добавить новое → перенести данные → удалить старое в следующей версии).
- Миграция, меняющая существующие данные, требует теста на копии реалистичных данных и явного упоминания в `UPGRADE.md`.
- Миграции применяются только явной командой `site migrate` (`make migrate`), никогда при старте.
  Порядок: модули в порядке из `site.yaml`, затем миграции сайта. Бинарник отказывается стартовать при непримененных миграциях.
- Перед применением миграций `site migrate` обязательно делает снимок БД (`VACUUM INTO`) и без него не продолжает.

**Тесты и документация к релизу**
- `testkit/` — контрактные тесты, которые сайт запускает у себя, чтобы убедиться, что интеграция не сломалась.
- `CHANGELOG.md` — для людей.
- `UPGRADE.md` — для агентов: для каждой версии, требующей действий, описать, что изменилось, какие изменения нужны в коде сайта, как проверить результат, нужна ли повторная обработка данных.

## Модуль изображений (первый)

- Загрузка, валидация, обработка (размеры, форматы), хранение.
- Хранилище за интерфейсом: локальный диск и S3-совместимое.
- У каждого файла хранится **версия профиля обработки**.
- Повторная обработка — штатная идемпотентная команда модуля («переобработать всё с версией профиля ниже N»), безопасная для прерывания и повторного запуска.
- Новые форматы и правила применяются к новым загрузкам автоматически, к старым — только через повторную обработку.
- Без CGO: ресайз — `golang.org/x/image/draw`, кодирование WebP — энкодер на WASM через wazero (`gen2brain/webp`).

**Профиль обработки v1**
- Оригинал хранится всегда (без него повторная обработка невозможна).
- Ширины 480 / 960 / 1600 / 2400 px, без увеличения.
- Выход: WebP q=80 и JPEG q=82 как фолбэк. AVIF — позже, новой версией профиля.
- EXIF удаляется; ориентация применяется до удаления.
- Лимиты: 20 МБ на файл, 40 мегапикселей (защита от decompression bomb).
- Вход: JPEG, PNG, WebP. HEIC не поддерживается (нет декодера без CGO).

## Спецификация сайта

- Формат: YAML, валидируется по `spec/schema.json`.
- Хранится в репозитории сайта как `site.yaml`.
- Описывает: разделы и типы контента (поля, связи, правила), подключённые модули и их версии, настройки (языки, SEO, хранилище).
- Структурные изменения сайта вносятся сначала в спецификацию, затем в код.
- Схему спецификации меняем осознанно: у неё есть версия, для старых версий нужен путь миграции.

**Версия схемы 1**
- Типы полей: `string`, `text`, `richtext` (Markdown), `int`, `bool`, `date`, `image`, `ref`, `slug`.
- Features: `draft`, `publish_date`, `rss`, `sitemap`.
- Ровно один язык: поле `languages` есть, но допускает один элемент. Мультиязычность — `spec_version: 2`.

Пример (ориентир, не окончательная схема):

```yaml
spec_version: 1
site:
  name: my-blog
  languages: [ru]
modules:
  images: v0
content:
  pages:
    fields:
      title: { type: string, required: true }
      body:  { type: richtext }
  posts:
    fields:
      title:    { type: string, required: true }
      body:     { type: richtext }
      cover:    { type: image }
      category: { type: ref, to: categories }
    features: [publish_date, draft, rss, sitemap]
  categories:
    fields:
      name: { type: string, required: true }
```

## Скиллы

Скиллы — тоже софт: версионируются, имеют эвалы в `skills/evals/`, обновляются вместе с модулями.

Распространяются как плагин Claude Code: монорепо — маркетплейс плагинов. Сайт указывает в своём `AGENTS.md`
минимальную версию плагина. Скиллы не копируются в репозитории сайтов: скилл обновления должен быть свежее сайта.

Эвалы требуют вызовов LLM, поэтому в CI запускаются вручную (`workflow_dispatch`) и обязательно перед релизом скилла.

Планируемые скиллы:
- **create-site** — задаёт вопросы, составляет `site.yaml`, создаёт репозиторий сайта по образцу `reference/`.
- **add-section** — добавляет тип контента: правка спецификации → код → миграции → тесты.
- **upgrade-site** — поднимает версии модулей, применяет `UPGRADE.md`, прогоняет тесты, готовит PR.
- **reprocess-images** — решает, нужна ли повторная обработка, и запускает её.
- **check-drift** (позже) — ищет расхождения между спецификацией и кодом.

Эвал скилла: по заданной спецификации результат собирается, проходит тесты и соответствует конвенциям эталонного сайта.

## Конвенции сайтов

Эталонная реализация — `reference/`. Любой новый сайт повторяет её устройство.
Если конвенцию нужно изменить — сначала меняется `reference/` и этот раздел, потом скиллы.

Каждый сайт содержит:
- `site.yaml` — спецификация;
- `AGENTS.md` — конвенции сайта и ссылка на используемые версии модулей;
- `CLAUDE.md` — одна строка `@AGENTS.md`;
- `Makefile` — единая точка входа (см. раздел «Makefile»);
- e2e-тесты ключевых сценариев (главная, раздел, публикация, загрузка изображения);
- запуск контрактных тестов из `testkit/` подключённых модулей.

Код сайта: стандартная библиотека Go, где её достаточно; `log/slog` для логов;
конфигурация через переменные окружения; один бинарник.

**Стек сайта**
- SQLite через `modernc.org/sqlite` (без CGO).
- Доступ к данным — sqlc; миграции — goose.
- Шаблоны — templ; интерактивность — htmx; стили — чистый CSS, без Node в сборке.
- Статика (CSS, `htmx.min.js`) вендорится и встраивается через `embed`.
- `richtext` — Markdown: goldmark + санитайзер HTML; в админке textarea с превью через htmx.
- Сгенерированный код (sqlc, templ) коммитится; CI проверяет, что генерация ничего не меняет.
- Линтер — golangci-lint с общим минимальным конфигом, версия закреплена в `Makefile`.
- Версия Go в `go.mod`: актуальный релиз минус один минор (сейчас `go 1.26.0`). Тулчейн разработки закреплён директивой
  `toolchain` (сейчас `go1.27.1`) в `go.work` и каждом `go.mod`; при `GOTOOLCHAIN=auto` Go скачивает его сам.
  Инструменты, запускаемые через `go run tool@vX.Y.Z`, вызываются с `GOTOOLCHAIN=$(GO_TOOLCHAIN)` из `Makefile`,
  иначе они соберутся старым тулчейном и не разберут код новой версии языка.

**Структура сайта**
```
cmd/site/main.go
internal/content/<type>/   # модель, sqlc-запросы, хендлеры, templ одного типа контента
internal/admin/            # оболочка админки и авторизация (пока здесь)
internal/web/              # layout, общие компоненты templ
db/migrations/             # миграции сайта (goose, своя таблица версий)
static/                    # CSS, htmx.min.js — через embed
site.yaml, Makefile, AGENTS.md, CLAUDE.md
```
Группировка по типу контента, а не по слою: `add-section` добавляет одну папку.

**Тесты**
- e2e на чистом Go: `httptest` + goquery; htmx-запросы — обычные HTTP с заголовком `HX-Request`.
- Немногие браузерные тесты критичных htmx-взаимодействий — chromedp, отдельной целью `make e2e-browser`.

**Эксплуатация**
- Основной вариант — бинарник под systemd на VPS; Dockerfile — опция.
- `make backup` (по cron): снимок БД и архив загрузок с локального диска. При хранилище S3 загрузки защищает версионирование бакета.
- litestream — опция, описывается в `AGENTS.md` сайта, но не обязательна.

## Makefile — единая точка входа

И в монорепо, и в каждом сайте все команды запускаются через `make`. Это касается людей, агентов и CI.

- Любая регулярная операция — отдельная цель: сборка, запуск, тесты, линтеры, кодогенерация, миграции, повторная обработка изображений, релиз и т. д.
- CI и скиллы вызывают только цели `make`, а не `go ...` напрямую. Если нужной цели нет — сначала добавь её в `Makefile`.
- Цель по умолчанию — `help`: выводит список целей с описаниями.
- У каждой цели есть комментарий `## ...` с описанием и, если она принимает параметры, примером вызова.
- Параметры передаются переменными с безопасными значениями по умолчанию (`VAR ?= ...`).
- В корне монорепо `test`, `test-isolated`, `lint` без `MODULE` проходят по всем модулям и `reference/`;
  `MODULE=<name>` — один модуль, `MODULE=reference` — эталонный сайт. `run`/`dev` делегируются в `reference/Makefile`.
- Совместимость с GNU Make 3.81 (стоит по умолчанию на macOS): без `.ONESHELL`, `$(file ...)` и других возможностей 4.x.

Пример оформления:

```make
.DEFAULT_GOAL := help

# Модуль в modules/<MODULE>. Комментарий — на отдельной строке: иначе пробелы попадут в значение.
MODULE ?= images

help: ## Показать список целей
	@grep -hE '^[a-zA-Z_-]+:.*## ' $(MAKEFILE_LIST) | awk 'BEGIN {FS = ":.*## "}; {printf "  %-20s %s\n", $$1, $$2}'

test: ## Тесты модуля. Пример: make test MODULE=images
	cd modules/$(MODULE) && go test ./...

test-isolated: ## Тесты модуля только на опубликованных зависимостях. Пример: make test-isolated MODULE=images
	cd modules/$(MODULE) && GOWORK=off go test ./...
```

## Зависимости

Правила действуют и для модулей, и для сайтов, и для инструментов (sqlc, templ, goose, golangci-lint, htmx).

**Перед добавлением или обновлением проверь**
- **Свежесть.** Берётся последняя стабильная версия, проверенная по реестру (`go list -m -versions <path>`, релизы на GitHub),
  а не по памяти: знания агента о версиях могут устареть. Не использовать pre-release (`-rc`, `-beta`),
  псевдоверсии (коммиты без тега) и `@latest` без фиксации конкретной версии — кроме случаев, согласованных с человеком.
- **Стабильность и поддержку.** У библиотеки есть теги semver, недавние релизы, живой репозиторий; она не помечена deprecated/archived.
  Лицензия совместима с MIT.
- **Совместимость.** Новая версия не конфликтует с остальными зависимостями:
  `go mod tidy` проходит без неожиданных изменений, в `go mod graph` нет двух мажорных версий одной библиотеки без причины,
  требуемая версия Go (`go` в её `go.mod`) не выше нашей политики версий Go.
- **Согласованность связанных пар.** Версии, которые должны совпадать, совпадают: CLI `templ` и библиотека `github.com/a-h/templ`,
  CLI `sqlc` и формат его конфига, `goose` CLI и библиотека.
- **Уязвимости.** `govulncheck` не находит известных уязвимостей в используемом коде.

**После изменения**
- Сборка, `make generate-check`, тесты и `make test-isolated` проходят.
- Версии инструментов закреплены в `Makefile` (`go run tool@vX.Y.Z` или директива `tool` в `go.mod`), а не берутся из окружения.
- Версия вендоренного `htmx.min.js` указана в имени файла или комментарии рядом.
- Для модулей: обновление зависимости, влияющее на сайты, отражено в `CHANGELOG.md` (и в `UPGRADE.md`, если нужны действия).

Цель `make deps-check` выводит доступные обновления (`go list -m -u all`) и запускает `govulncheck`; она входит в CI.

## CI

GitHub Actions; джобы вызывают только цели `make`.
- Path-фильтры: изменения в `modules/<X>` запускают джобы для `<X>` и для `reference/`.
- Модуль: `make lint`, `make test`, `make test-isolated`, `make generate-check`, `make deps-check`.
- `reference/`: то же плюс `make e2e`, всё с `GOWORK=off`.
- Эвалы скиллов — вручную (`workflow_dispatch`).

## Как работать агенту

1. Перед изменениями прочитай этот файл и затронутую часть `reference/`.
2. Меняешь публичный API модуля — оцени, мажорное ли это изменение, и обнови `CHANGELOG.md` и `UPGRADE.md`.
3. Команды запускай через `make` (список — `make help`). После изменений: проверки и тесты затронутых модулей, в том числе с `GOWORK=off`, — через соответствующие цели.
4. Не выноси код в новый модуль и не добавляй внешние зависимости без согласования с человеком. Перед добавлением или обновлением любой зависимости выполни проверки из раздела «Зависимости».
5. Миграции, меняющие существующие данные, и изменения схемы спецификации — только после явного подтверждения человеком.
6. Если конвенция не описана — посмотри, как сделано в `reference/`, и предложи дописать правило сюда.

## Первый этап

1. Модуль `images` с тестами, testkit и миграциями.
2. Черновик `spec/schema.json` для страниц и блога.
3. Эталонный сайт `reference/`: обычные страницы + блог + админка с авторизацией, использует `images`; SEO, sitemap и RSS — в коде сайта.
4. Скиллы `create-site` и `upgrade-site` с первыми эвалами.
5. Второй сайт, созданный через `create-site`. По его итогам: что реально переиспользовалось, насколько точно агент воспроизвёл конвенции, что улучшить перед новостями и каталогом.

## Принятые решения

Решения ниже приняты человеком; не пересматривать без него.

| Вопрос | Решение | Почему |
|---|---|---|
| Путь модулей | `github.com/keelkit/keelkit`, без vanity-домена | домена нет; имя на GitHub свободно |
| Видимость и лицензия | публичный репозиторий, MIT | приватные модули ломают `go get` у старых сайтов |
| СУБД | SQLite (`modernc.org/sqlite`, без CGO) | один статический бинарник; хватает для целевых сайтов |
| Доступ к данным | sqlc | ошибки типов ловятся на генерации, а не в проде |
| Миграции | goose, таблица версий на модуль | свой мигратор привёл бы к дублированию или core-модулю |
| Шаблоны и фронт | templ + htmx + чистый CSS | ошибки шаблонов ловит компилятор; без Node |
| Изображения | x/image + WebP через wazero | без CGO; профиль версионируется, можно сменить |
| Авторизация | в коде эталона, одна таблица пользователей | вынос в модуль — после второго сайта (принцип 6) |
| Версии модулей | `v0.x` до второго сайта, затем `v1` | API подтверждается двумя сайтами |
| Скиллы | плагин Claude Code из монорепо | скилл обновления свежее обновляемого сайта |
